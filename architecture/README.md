# CodeSage 架构

[English](README.en.md) · [返回首页](../README.md)

CodeSage 把一次代码审查分成两个相互配合的部分：平台负责让任务可靠地执行，Deep Review 负责把变更调查清楚。Web 提供项目和任务入口，队列将工作交给 Worker，审查引擎组织模型读取代码、提出问题、核验证据，再把结果交回平台。

本文按这一统一架构展开。Web / Worker 与 Deep Review 的接入正在落地；下面的整合视图描述它们的设计关系。

## 从提交审查到拿到结果

![CodeSage 统一架构：入口、任务治理、深度审查与结果](../assets/media/codesage-architecture.svg)

开发者提交仓库和要比较的两个版本。平台保存任务，通过 ARQ 将任务送入队列。Worker 认领执行权后启动审查，运行期间持续续约，完成后通过提交门禁写入结果。Web 展示任务进度和审查意见；本地 CLI 则直接调用审查引擎，适合调试、脚本和基准测试。

这几个部分各管一件事。API 不承担长时间的模型对话，队列不决定谁有权提交结果，Worker 不替审查引擎判断代码问题。Deep Review 也不需要知道任务来自 Web 还是命令行，它接收固定的代码版本和审查配置，产出报告与运行记录。

假设一个 PR 把鉴权逻辑从路由函数移到公共中间件，同时修改路由注册和测试。只看新增的中间件，很容易认为改造已经完成。真正要回答的是：所有受保护的路由都挂上了中间件吗？异常处理是否改变了拒绝访问的行为？测试覆盖的是实际部署时使用的路由吗？Deep Review 的工作，是把这些问题变成可以沿代码验证的调查。

## 审查之前，先把代码准备好

一次审查始终围绕固定的 base 和 head 提交。运行途中工作区发生变化，不会让某个 Reviewer 读到另一版代码。差异在开始时解析并保存在内存中，后续读取文件和搜索代码也使用同一个 Git 快照。

目录过滤将文件分成需要审查的变更、可供参考的上下文和排除内容。生成文件、二进制和敏感路径不应占据模型的调查时间。其余文件先经过结构整理：哪些目录发生了变化，代码与测试分别改了多少，哪些文件可能互相影响。

Anatomy 将这些信息整理成变更概览。Blast Radius 则补充依赖线索：对于 Python 变更，它分析 import 关系，找出直接依赖变更模块的文件。在鉴权改造的例子里，即使调用者没有出现在 diff 中，它仍可能是理解行为变化的重要入口。这些步骤由代码完成，不需要模型重复数文件、统计行数或猜测目录关系。

Semantic 随后阅读 PR 描述、提交信息、结构概览和有界的 diff 摘录，写出一份简短的意图分析。它帮助后续审查理解“这次改动想做什么，以及哪里值得追问”。这份分析保留假设的性质：PR 声称统一了鉴权，不等于代码已经覆盖了所有路由。判断仍要落到源码上。

## Planner 分配调查，而不是预先宣布问题

![Deep Review 从固定输入到最终报告的审查流程](../assets/media/deep-review-flow.svg)

Planner 将变更组织成几项内聚的调查工作。每项工作说明要审查的文件、需要参考的上下文、调查问题和优先级。关联文件可以放在同一个维度里，不必按文件机械分组。

对于上面的 PR，一个维度可以检查中间件的拒绝访问行为，另一个检查路由注册是否完整，第三个检查测试与部署配置的对应关系。这里没有要求模型发现三个缺陷。这三项只是调查任务，结果可以是发现问题，也可以是证明某个怀疑不成立。

目标文件决定 Reviewer 的审查范围；上下文文件帮助理解调用关系和约定。优先级决定工作顺序，不代表问题严重程度。Planner 还可以留下跨维度线索，比如“将路由注册结果与部署入口对照”，交给后面的 Cross 验证。

模型生成的计划需要经过代码整理。路径错误会被拒绝，遗漏文件会补入通用审查，过大的任务会拆分。更容易出错的地方是重复维度：如果两个任务都调查同一组文件，简单删掉其中一个会连调查问题一起删掉。

CodeSage 只合并完全被一个已有维度包含的后续任务，并保留它的调查问题和上下文。比如“检查中间件和路由注册”已经包含两个文件，后面单独针对中间件的调查可以合进去。但“中间件”与“中间件、路由注册、部署入口”仍保留为两项工作，后者需要完整的跨文件上下文。相关维度的名称映射也随之更新，避免 Cross 的线索指向已经消失的任务。

这种处理允许有理由的重叠，却不会为相同范围重复创建大量 Reviewer。计划是调查起点，不是 Reviewer 的结论，也不是它只能发现这些问题的限制。

## Reviewer 一边调查，一边判断评论是否值得提交

每个 Reviewer 有独立的会话，读取自己的目标 diff，并通过工具追查更多代码。并发由共享限制控制，调查轮次按文件规模分配。小任务不必承担大任务的成本，大任务也能获得更多阅读空间。

工具保持简单，所有角色都使用同一套只读能力：

| 工具 | 用途 |
| --- | --- |
| `file_read` | 读取固定 head 中的完整文件片段。 |
| `file_read_diff` | 读取缓存的某个文件差异。 |
| `file_find` | 按文件名查找路径。 |
| `code_search` | 在固定版本中搜索字面量或正则。 |

Reviewer 不只是对照 Planner 的问题打勾。它要找出具体触发条件，检查相关分支是否可达，沿调用者和消费者验证后果，再考虑有没有足以推翻结论的无害解释。怀疑某个路由绕过鉴权时，它需要找到路由注册与中间件挂载的实际关系，而不是看到一个没有鉴权调用的函数就下结论。

评论价值判断也在这轮调查中完成。Reviewer 要说明哪里有问题、什么情况下发生、会造成什么影响，并给出直接的修复方向。命名、文档和风格问题不被一概排除，但一样需要具体依据和实际价值。这样不必再开一个独立的模型阶段，重新阅读相同材料来判断“这条评论是否值得发”。

候选意见提交时经过结构与位置校验。文字过长会截断，不会仅因超长就丢掉整条 Finding。某个 Reviewer 失败时，其他维度的结果继续保留，过程报告也会明确记录没有完成的调查范围。

## Cross 将局部发现放回整个变更中验证

并行审查擅长深入局部，也容易产生互相重复或缺少另一端证据的结论。Reviewer 的输出因此先作为候选，而不是直接作为最终评论。

代码为每条候选提取附近源码和对应的变更片段，再组装 Cross 的输入。所有候选都保留，使用稳定索引关联证据；相同 diff hunk 只发送一份。对于没有具体行号的整体性问题，会说明为什么无法匹配 hunk，不会伪造一个位置。

Cross 收到的是候选主张、必要的变更证据、跨维度线索和审查覆盖情况。它不再接收整份 Semantic、Plan 或所有 Reviewer 对话。那些材料帮助过调查，但继续全量传递会增加重复信息，也可能让早期推测影响最终判断。需要更多源码时，Cross 使用同一套工具读取。

这一轮验证同时处理几类问题：证据是否支持结论，最强的无害解释能否成立，跨文件的生产者与消费者是否一致，多条候选是否指向同一个根因，以及它们是否组合成新的独立风险。

在鉴权例子里，中间件 Reviewer 可能认为异常分支会放行请求，路由 Reviewer 则发现某组路由没有挂载中间件。Cross 要分别验证两条结论，再判断它们是否只是同一个问题的两种描述。它还可以检查部署入口是否使用了另一套路由注册，找到局部审查没有连接起来的证据。

Cross 按候选索引返回保留或删除的决定、理由和必要的严重度调整，新增复合问题单独返回。没有明确裁决的候选不会凭空消失；删除必须有理由。验证失败会留下未解决风险和部分完成状态，而不是把没有验证的范围写成“没有问题”。

## 模型负责调查，代码负责边界

Deep Review 在需要理解意图和追查行为的地方使用模型，在筛选、覆盖修复、证据提取、位置校验和结果整理上使用确定性代码。把每一步都做成 Agent 不会自动带来更好的审查，只会增加延迟、重复上下文和失败点。

Semantic 是一次结构化生成。Planner、Reviewer 和 Cross 使用 Harness：模型可以多轮调用工具，直到通过 `FinalizeReview` 提交符合阶段 Schema 的结果。终结有独立的有界请求路径，不能靠不断增加轮次来等待模型自行结束。

模型兼容也在这里处理。支持思考模式下强制工具调用的模型，可以保留调查消息前缀，追加终结要求；需要特殊处理的端点则使用兼容策略。相同的审查流程不必为每个供应商重写，消息组织也尽量保留可复用的缓存前缀。

最终收尾不再调用模型重写意见。代码接纳 Cross 裁决，清理格式，精确去重，按严重度和质量信息排序，再生成稳定的报告。每个阶段都有输入范围和输出约定，模型负责范围内的调查，而不是同时控制任务生命周期、文件访问和最终提交。

## Worker 为什么需要租约和提交门禁

深度审查可能持续数分钟。队列重复投递、Worker 重启或网络中断都可能让同一个任务出现两次执行。仅凭“从队列取到了消息”判断执行权，会让两个 Worker 都认为自己应该写回结果。

CodeSage 用数据库中的租约决定谁是当前有效执行者。认领时加行锁，检查任务状态与已有租约，再分配新的执行代次 `lease_epoch`。Worker 通过心跳续约；续约只接受匹配的 owner 和 epoch，且租约必须尚未过期、任务未被取消。

假设 Worker A 认领任务后失去响应，租约到期，Worker B 接手。A 随后恢复并完成了模型调用，它的结果仍不能写回。提交门禁会再次检查执行权，发现 A 持有旧 epoch，拒绝这次提交。B 的有效结果不会被较晚到达的旧结果覆盖。

结果、阶段记录和任务终态在同一事务中提交。取消请求让执行权失效并停止本地工作；恢复执行使用新的代次。平台因此管理的是“谁有权完成这个任务”，而不只是“进程有没有在运行”。已经发出的模型请求仍可能产生费用，提交门禁保证的是有效结果不会被旧 owner 覆盖。

## 报告与运行记录

审查结束后，读者可以从两个角度看结果。最终报告面向要修改代码的人：问题位置、严重度、说明、修复建议和未解决风险。过程报告面向要理解审查的人：变更概览、语义分析、计划 Draft 与修复结果、各 Reviewer 的输出、证据以及 Cross 的裁决。

工具调用和模型消息保留在会话记录中，阶段事件与用量帮助解释运行过程。发现 Recall 低时，可以追问是计划遗漏了调查方向，Reviewer 没读到调用者，还是 Cross 错误删除了意见；运行缓慢时，可以查看重复读取、无效工具调用和终结重试，而不是只看到一个总耗时。

平台任务与最终业务结果使用 PostgreSQL，ARQ 使用 Redis，Phoenix 接收 Trace。本地 CLI 将审查事件写入 JSONL，用 SQLite 保存 Harness 会话，同时导出最终报告和过程报告。源码快照仍是模型读取代码的依据，事件记录和遥测不替代它。

AACR-Bench 也调用同一审查引擎。适配层只负责启动、等待、结果转换和归档，不针对参考答案改变审查过程。公开的 GLM-5.2 汇总记录了 100 个实例，精确率 52.8%、Recall 23.4%、F1 32.4%。这些数值描述端到端效果；诊断一个具体问题，还要回到对应的阶段输出和会话轨迹。评测文件中的汇总与缺失实例元信息有统计差异，比较时应保留样本口径。
