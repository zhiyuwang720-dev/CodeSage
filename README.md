对于一个 Agent 或者 Harness来说， 真正的地基是什么， 而哪些又是外部扩展， 这是我们第一个需要清楚的问题

我们可以从2个角度进行划分

1. 去掉它，循环还能跑吗—— no sub-agents / no plan mode / no permission popups / no MCP / no todos / no background bash，但它依然是一个完整 Harness。这些全被证伪为"非地基"。
2. 替换成本——换沙箱（bwrap→e2b）、换 eval 框架、换 UI 都不动主循环， 这些都不是地基。 但是换消息形状、换循环语义就要动一切。


我们可以得到结论：

地基（内核）为六根柱子

1. 消息契约 : LLM 只认 user/assistant/toolResult 三种角色，所有信息必须归一到这里。换它等于重写一切
2. 主循环或者类似循环的结构 :   这是 "运转"本身。 UI、审计、eval 全部靠循环产生的事件流驱动     
3. 会话与状态 ： 长任务、断点恢复、多轮上下文全在这里
4. 模型抽象  ： 不抽象出统一的模型层，换模型等于重写 harness      
5. 工具契约  ： ReAct 的"另一半"， Agent 的基础
6. 宿主接口  ： 入口可以有多种形态，但不能没有      


注意：可观测性机制（属于会话与状态）是内核，让循环的每一步可被外部观察/重建。 而可观测性产品是扩展——TUI、审计面板、日志分析工具都是坐在这个机制之上的应用层。
注意：拦截点（属于主循环）是内核，策略是扩展 —— 很多策略看起来"内核级"，实际都是坐在钩子上的：
    - 权限：beforeToolCall（可 block + terminate）是地基；deny>ask>allow 怎么排、谁审批是策略。
    - 循环控制：turn 停止钩子是地基；turn budget、token budget continuation、nudge 是策略。
    - 记忆：上下文管线（注入位置）是地基；何时压缩、怎么总结、要不要长期检索（FTS/向量库）是策略。
    - 沙箱：工具执行的边界机制是地基；bwrap 还是 Landlock 还是云端隔离是策略。

调度算法 = 三机制混合

① 静态装配（预先分配）——启动时一次性
基础 system prompt（pi initialState / DSH system-prompt 在 core spine）、工具 schema、skill 目录索引、模型档位（DSH 的 summarizationProvider/Model 空值回退链：最近请求目标 → AgentOptions——这就是 CodeSage 模型指针
main/task/compact/quick 的源头）、DSH context 插件族（time-context / tmux-context / agent-instructions / file-reference 的 @file）按 bundle 配置预启用、每请求注入。

② 事件驱动 + 阈值触发（动态，决策点固定在循环边界）
- DSH：agent/pre-step 串行监听器在请求派生前查 token 压力（ctx.tokenMeter 计量）；agent/request-error 处理溢出恢复
- pi：transformContext 每次 LLM 调用前跑（prune/inject 全权）；shouldStopAfterTurn 每 turn 后判断（示例就是 shouldCompactBeforeNextTurn）
- 这相当于"时钟中断"：循环的 step/turn 边界就是检查上下文状态的固定中断点

③ 模型驱动拉取（动态，内容的真实流动）
skill 正文、session-query 检索结果、file-reference 展开——全是模型自己调工具"拉"的。系统从不决定"模型该看什么"，只保证"页表在 + 拉取路径可用"。

预先分配还是动态规划？——骨架预分配，血肉动态规划

两者不矛盾，分界清晰：
- 预分配：页表（catalog）、参数（thresholdRatio=0.8 / retainRatio=0.16）、模型角色（compact 档位 + 回退链）、注入器集合（context 插件族）
- 动态：压缩时机（压力事件）、保留窗口计算（按路由模型的实际容量）、召回内容（模型自拉）、注入位置（transformContext 全权 / context modifier）、skill 正文（按需加载）

一句话总结

上下文工程的调度算法 = 静态装配页表 + 循环边界事件驱动的压力回收 + 模型自拉的按需调页。调度器的本质是看守者不是安排者：在 step 边界监控 token
压力、溢出时强制换出、空闲时后台回收——但"进程看什么内存"由模型自己决定。这正是它像内核态/用户态交换器的原因：内核管"怎么换"，用户态管"要什么"。



两种调度实现哲学 ： 微内核单点调度：transformContext + shouldStopAfterTurn 两个 hook 收拢全部上下文决策，compaction 默认实现挂上去，策略在用户态。决策点集中、职责单一。
宏内核服务化调度：token-meter（测量）、compaction-basic（回收）、tool-result-pruner（回收前预清理）、context 族（静态注入）、skill（按需调页）各是独立服务，通过事件总线（pre-step / request-error）协作。任何一块可换。



设计：三合一的"事件溯源 + 状态机 + 分层契约"
核心主张：内核 = 状态机 + 事件日志， 扩展 = 三面隔离接口。

第一层：内核（六根柱子，只做机制）

- 消息模型（唯一形状，Anthropic ContentBlock 式）
- 显式状态机主循环：不是 while 循环，而是 turn/step 生命周期——每个决策点（pre-step / tool-preflight / tool-execute / tool-result / request-error /
  turn-end）都是固定编号的中断点：可观察（事件）、可拦截（同步干预）、可回滚（日志投影）
- 事件日志即会话：append-only JSONL/SQLite，内存状态 = 日志投影。崩溃恢复 = 重放；resume/fork/审计/debug/无 key 测试全部免费
- 上下文管线：transform → 注入 → convert 三阶段，每阶段有 hook（token 计数、硬截断兜底是内核的）
- 模型抽象：provider + 模型角色（main/task/compact/quick）+ 回退链
- 工具契约：schema → 校验 → 执行 → 结果回填，失败永远转 error tool_result

内核验证法用 pi 的：逐个砍，砍完还能转 → 留下的是真内核。

第二层：Seam（契约层，内核与插件的分界线）

每个能力一个显式契约，三件套定义：

能力 X = 服务接口（ctx.x 的 Protocol）+ 事件词汇表（x/start, x/end, x/error）+ 模型可见面（工具/context modifier）

DSH 的 capability seam 已经证明这条路能走到 60 包不塌。我的改进是加一条硬约束：

▎ 插件之间禁止直接耦合——只能通过事件日志和内核服务注册表交互。

这一条防的是插件网络退化成意大利面。DSH 靠 Cordis 的 DI 图天然解耦，但在 Python 里没有这个机制兜底，必须把"插件只能看见内核 + 自己依赖的服务"写成纪律和测试（conformance test：插件 A 的单元测试不允许 import 插件 B 的实现）。

第三层：插件（全部策略）

权限、压缩、spill、沙箱、skill、检索、多 Agent、eval——全在 Seam 之上。默认策略内置但不写死（像 DSH compaction-basic：默认 thresholdRatio=0.8），任何策略可整体替换。

稳定性机制（针对"极其稳定"）

1. 日志事务：所有写会话的操作是带锁事务（compaction 的 start/summary/end 就是锁）；崩溃产生的是"可检测的孤儿锁"而不是损坏状态
2. 看门狗机制进内核，参数进插件：turn budget、deadline、runaway 检测的机制（计数器、超时、终止事件）是内核的；策略值（几个 turn、几秒）是插件配置
3. 插件隔离：插件崩溃包在 try/wrap 边界里，不杀循环；插件错误转事件，不转崩溃
4. 契约测试：每个 seam 一条 conformance suite，行为合同自动化验证——这是"极其稳定"在工程上的落点，不是设计文档

扩展性机制（针对"高扩展"）

1. 新能力 = 新服务 + 新事件 + 新工具三件套，零内核改动（DSH 用 60 包验证过这条）
2. 事件流是扩展总线：UI、审计、遥测、eval 全是事件消费者，内核不为它们开 API
3. 模型面冻结：模型只见工具 + 消息；新能力永远通过"新工具"暴露，模型契约不漂移

落到 CodeSage 的具体形态

你正在移植的 engine/ + core/session 正好是这套架构的前两层：engine 做成显式状态机（每个决策点一个编号事件，loop_markers.py 已经在往这个方向走），session 做成事件溯源日志。下一步的落点是：把 compaction/permissions 接成走 seam
的插件而不是引擎内 if 分支——代码里现在还能看到哪些策略是写在引擎里的，把它们往外推一层，就是这套架构的 Python 化。

一句话总结设计主张：内核给机制和日志，seam 给契约，插件给策略；稳定靠"日志可重建 + 契约测试 + 看门狗机制"，扩展靠"三件套 + 事件总线 + 模型面冻结"。




内核评测的关键判断先说：内核评测必须是无模型（model-free）、确定性、CI 可跑的——这和 Agent 能力评测（judge/eval）是两码事。内核是确定性机制（状态机、事件日志、工具契约），不该用"模型聪不聪明"来测；模型行为全
mock/录制掉，剩下来的正确性才是你的内核问题。

第 1-3、5 层测内核，第 4 层测系统——分层评测的价值：judge 分数低时，1-3 层全绿就把内核问题完全排除，归因直接跳到模型/工具/上下文策略。

各层怎么落地

第 1 层：seam conformance suite——每条 seam（工具契约、消息契约、会话契约）一个测试文件，用 stub 模型（按脚本返回预置响应）。断言"行为合同"：工具失败必须转 error tool_result、消息只有三种角色、事件日志 append-only。

第 2 层：状态机穷举——从每个 phase 出发调每个公开方法：preStep() 在非 running 态必须 throw（DSH 自己的守卫就是现成测试素材）；turn/step 计数单调；abort → wakeRequested → 恢复路径；重复 prompt 必须拒绝重入。

第 3 层：这是你的设计红利——因为决策事件也进日志，"跑一个完整会话后断言事件日志序列"就是最强大的验证：每次 pre-step 为什么发生、压缩何时触发、每个事件与预期序列逐项对比。加上故障注入：工具超时、provider
溢出（context-overflow）→ 断言走 request-error 恢复链。崩溃恢复测试不用 mock——直接 kill 进程，重放日志，断言会话可继续。

第 4 层（上层，晚点做）：pi evals 模式——harness + judge + evalHarnessTable 对比（换模型/换 prompt 测 lift）。DSH snapshot（keyless replay）和 CodeSage 现成的 CODESAGE_VCR=record|replay 是第 3
层的现成资产——录一次真实交互，回放做回归，无 key 也能跑 CI。

第 5 层（稳定性承诺）：把"极其稳定"变成可量化门禁——kill 恢复成功率 100%、日志不变量零违规、compaction 事务（start→summary→end）零孤儿锁、工具执行超时率。做不到就红 CI，这才是"稳定"的工程定义。

2. 第 3 层用现成 VCR——把"决策日志断言"作为主验证手段
3. 内核稳定后再搭第 4 层（pi evals 移植）——别提前做，模型评测工具会拖住内核迭代
4. 一个提醒：win-mtime-flake 那类平台问题，说明你的测试基础设施本身也要稳定——VCR 回放天然免疫这类 flake，这也是选择录制回放路线的额外理由
