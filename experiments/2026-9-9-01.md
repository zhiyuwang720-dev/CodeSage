问题一： Agent运行过程中出现以下信息：


环境探测结论明确：工作区目录不存在，Read/Glob/Grep/Bash 全部失败，仓库源码在本次会话中不可访问。因此无法读取源码核实调用链（例如 modelSupplier 的定义、getSubGroupsCount() 的上游调用方、GroupUtils 删除方法的调用点）。
基于唯一可用的证据——diff 文本——完成安全视角分析：



1. 核心问题分析 (Current Pain Points)
无效的 Agent 探索循环（Token 浪费）：由于环境（工作区目录）缺失，Agent（LLM）在收到任务后，不知道环境不可用。它只能通过试探性地调用工具（Read/Glob/Grep/Bash）来尝试获取上下文。一次、两次失败后，Agent 可能还会尝试换路径、换命令，导致大量无效的 LLM Token 消耗（包括工具调用的输入输出 Token）。
错误信息产生“幻觉”：Agent 在没有源码的情况下，被逼无奈只能“基于 diff 文本”做分析。这种分析很可能会导致它去“猜”源码的定义（例如猜测 modelSupplier 是什么），从而在代码审查中产生严重的幻觉（Hallucination），给出错误的结论。
推理成本极高：每次工具调用失败，Agent 都需要重新规划下一步，浪费了宝贵的推理步数和时间。

2. 优化方案解析 (The Proposed Solution)
将“环境探测”从 Agent 的运行时行为，转变为“静态前置校验”。
前置校验层（Python Code）：在触发 Agent 之前，直接用一个轻量级的 Python 脚本（或宿主机逻辑）检查：工作区目录是否存在？仓库是否已克隆？关键文件是否可读？
系统提示词注入（Context Injection）：如果在 Python 层判断为“环境不可用”，则直接将探测结果（例如：“警告：当前环境无法访问源码，仅提供 diff 文本，禁止进行源码溯源”）作为系统级提示词（System Prompt）强注入给 Agent。

3. 具体的优化落地（如何做得更好）

打破 Agent 的“侥幸心理”：注入的提示词不能仅仅陈述事实，必须包含硬性约束（Hard Constraints）。例如：
1） "System: 工作区 '/workspace' 不存在，且 Git 仓库不可访问。你不得调用 Read/Glob/Grep/Bash 等任何文件系统工具。请直接根据提供的 Diff 文本进行纯静态逻辑分析。"
这直接切断了 Agent 尝试调用工具的欲望，节省了 Tool Call 的 Token。
2） 强制降级模式（Graceful Degradation）：在 Python 层面，如果探测到环境不可用，不要直接调用完整的 Agent 流程。而是限定该次任务为“Diff-only 审查模式”，并可以关闭某些复杂的工具（在代码中直接禁用工具注册表）。
3）提前暴露错误结果而非任由 Agent 浪费：Python 代码判断环境缺失后，甚至在注入提示词之前，直接在任务运行列表中标记一个标签（例如 Environment: Unavailable），让后续的评分、日志记录知道这次分析是受限的。

4）权限控制（Permission Level）：为 Agent 提供一个“最小化工具集”的回退配置。如果前置检查失败，只给 Agent 提供 Read only diff 的权限，而不是给它全套的 Bash/Grep 权限。



问题二：

在 PR（Pull Request）评审 这个特定领域，直接给 Agent 授予 WRITE（写文件）、BASH（执行命令）、甚至广义的 READ/GREP（读取/搜索整个文件系统）权限，不仅大材小用，而且极其危险且低效。
应该设计单独的工具


1. 为什么这四个工具不适用于 PR 评审领域？
WRITE（写）：评审 Agent 的职责是审查和提出建议，而不是修改代码。如果允许 Agent 写文件，它极有可能因为幻觉直接篡改代码，导致严重的生产事故。直接移除 WRITE。
BASH（执行命令）：评审 Agent 不需要运行构建、跑测试或执行脚本。让它拥有 BASH 权限，除了增加巨大的安全风险（如执行恶意命令），还会导致它为了“探查”环境而盲目尝试命令，浪费大量 Token 和时间。直接移除 BASH。
READ / GREP（全盘读取/搜索）：PR 评审的核心上下文是 Diff（变更），而不是整个代码仓库的历史。将整个工作区暴露给 Agent，会导致它去搜索无关的代码，导致上下文窗口被无关代码填满，干扰对核心 Diff 的判断。


2. 如何设计“PR 领域专属工具”   （简易思路，需要严格最大强度思考）
就是将原生的通用工具（Bash/Grep/Read）替换为领域特定的、具备严格参数限制的工具。
推荐的工具集：
read_diff_file(file_path)：核心工具。只允许读取本次 PR 变更过的特定文件（由 Python 前置代码计算好 Diff 文件列表，把白名单传给 Agent）。

search_in_diff(keyword)：上下文搜索工具。只允许在 Diff 的文本内容中进行搜索，而不是全局的 Grep。

fetch_repo_metadata(file_path, line_num)（受限的读取）：允许 Agent 读取 Diff 中涉及到的特定行附近的少数上下文代码，但必须限制行数范围（例如只允许读上下各 20 行），而不是让它读整个文件。

get_commit_history(file_path)：用于查看该文件最近相关的提交记录，辅助判断代码演变趋势。

坚决剔除的工具：
剔除 WRITE 和 BASH（决绝不给）。 替换 Grep 和 Read 为上述带参数限制的检索工具。


动态构建一个仅包含上述 3-4 个 PR 专用工具的列表传给 Agent。
强制上下文注入：在调用 LLM 前，将变更文件列表（File List） 和 Diff 文本预先放入 System Prompt 中，告诉 Agent：“你只能使用 read_diff_file 读取我提供给你的文件列表，不能访问其他文件”。
