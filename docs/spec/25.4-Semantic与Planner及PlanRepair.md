# Spec 25.4：Semantic、Planner 与 Plan Repair

版本：1.0。状态：待实施。依赖：25.3A 已完成。
上位设计：[Plan25](../plan/25-CodeSageDeep-V1核心移植与原型闭环.md)，重点阅读 5.2、5.3、6.4～6.6。公共规则见 [总索引](25-CodeSageDeep-V1核心移植与原型闭环.md)。

## 1. 阶段描述

本包在 Anatomy 后接入一次 Semantic .ai() 和一次 Planner .harness()。Semantic 生成待验证的整体叙述；Planner 划分调查职责和文件覆盖；确定性 repair 把模型建议转成可信的工作分配。

交付后 --through planning 可以运行到修复后的 ReviewPlan，报告仍为 pipeline_complete=false。同一入口的 --through anatomy 必须继续离线可用。

## 2. 文件与开发范围

| 文件 | 责任 |

| agents/planner.py | 私有 Planner Draft、输入构造、Harness 调用、调用 repair |

| schemas/pipeline.py | 更新 SemanticBrief、ReviewPlan、ReviewDimension、业务 CrossReferenceHint |
| schemas/output.py | 扩展 preparation report 到 planning，增加可选 semantic/plan |

不要新增 Draft 公共包。不要把业务模型直接当 FinalizeReview schema。Draft 仅在 Agent 内定义，Agent 调用 mapper/repair 后返回 AgentCallResult[业务模型]；orchestrator 只处理业务结果。

## 2.1 观测契约

`AgentCallResult` 是唯一调用级元数据载体，保留 `value/error/session_id/usage/cost_usd`。orchestrator 在阶段成功、fallback 或失败后将其转换为 `AgentObservation`。

`schemas/output.py` 新增 `AgentObservation(stage, session_id, usage, cost_usd, error=None)`。本包 Literal 为 `"semantic"` 和 `"planning"`。`PreparationReport.agent_observations` 保存两条调用观测。

Semantic 使用 `.ai()`；当前 RuntimeBridge `.ai()` 不创建 AuditSession，因此 `session_id=None` 是明确契约，不得伪造。Planner 的 `session_id` 必须来自 `HarnessResult.session_id`。usage/cost 可得则原样透传；不可得为 `None`，不得补零。

阶段事件 `semantic_completed/semantic_fallback/plan_completed/plan_failed` 写入上述观测和短 error；不写 prompt、完整响应、transcript 或 provider 请求体。CLI stderr 打印一行无敏感内容的 `deep_review.agent_completed` 摘要，包含 session 是否存在、主要 token 字段和 cost 是否可用。

## 3. Runtime 接入的真实前提

当前 services/runtime.py 只有 Protocol、Factory Protocol 和 AgentCallResult，还没有真实 factory。必须在本包实现，否则 CLI 虽有 planning 参数却不能真实运行。

现有 RuntimeBridge 构造需要 llm_service、tools，可注入 session_factory 和 agent_type。ai 支持 system/schema/max_tokens；harness 支持 schema/cwd/system_prompt/max_turns/tool_allowlist/tools。请按实际签名调用，不能将模型角色名作为不存在的 model 参数传入。

Factory 接收现有 LLM 服务和可选 session_factory，for_role(role) 构造配置 agent_type=role 的 bridge 薄包装。每次 Harness 调用创建独立 session。静态角色资源可以复用，运行中的 session/state 不得跨并行调用复用。Provider 配置沿现有 LLM 服务入口解析，不复制一套 API key 配置系统。

真实 Harness 仍依赖 AuditSessionStore。模型调用前明确检查所需配置，缺失时失败；不要自动建表或运行迁移。fake factory 的全流程测试必须不连接数据库。--help 和 anatomy 不得初始化真实 factory。

## 4. Draft 与业务模型契约

所有 Draft 使用 extra="forbid"，所有字段提供 description；列表条数约束与字符串长度约束分别设置。完整字段形状按 Plan 5.2、5.3，以下是实现必须满足的语义。

SemanticBriefDraft 包含 narrative、stated_intent、implemented_intent、intent_gaps、unrelated_changes、risk_surfaces、hypotheses、confidence。narrative 长度 20～2000；六个列表最多 20 项，每项 1～200 字符；confidence 在 0～1。列表元素长度要通过 Annotated[str, StringConstraints(...)] 等实际校验实现，不能只写在 description。

业务 SemanticBrief 逐字段从 Draft 构造，并由代码填 source=model。fallback 使用相同业务类，source=fallback、confidence=0，narrative 来自有界 title/description/commit subjects/Anatomy 统计；线索列表可为空。不能用 confidence=0 代替 source 标志。

ReviewDimensionDraft 包含 name、review_prompt、target_files、context_files、priority、rationale。name 为 1～64 字符，模式为 ^[a-z0-9][a-z0-9_-]*$；review_prompt 为 20～2000；priority 1 最高、10 最低。target_files 非空。ReviewPlanDraft 包含 summary、dimensions、cross_reference_hints、assumptions。最多 32 个模型 dimension、16 个 hint、10 个 assumption。

CrossReferenceHintDraft 只有 dimension_names、relation、symbol_or_contract，分别说明参与的至少两个维度、需验证的关系和定位依据。业务 CrossReferenceHint 单独定义，不能嵌套 Draft。

fallback/deferred/source/coverage_complete/repair_actions 都由代码生成。Schema 校验只能证明格式符合要求，不能证明模型的代码判断正确。SemanticBrief 在下游始终作为不可信线索。

## 5. Draft 如何进入 repair

采用明确、无循环依赖的做法：Planner Agent 在解析成功后调用 draft.model_dump(mode="json")，将这个局部输入字典交给 repair_plan；repair_plan 通过显式字段构造业务类。这里的字典只存在于紧邻的映射边界，不能作为跨阶段状态或公共 output。

repair_plan 同时接收 snapshot、config 和确定性合法上下文路径集合。services/plan_repair.py 不 import agents/planner.py，agents/planner.py 可以 import repair_plan。不要创建通用 DTO 转换框架，也不要在 schemas 中引用 Draft。

## 6. 阶段输入构造

Semantic 输入包含 title、description、snapshot.commit_messages、允许变更集的 Anatomy 紧凑摘要和 diff 摘要。不要读原始 snapshot.changes 中已经排除的 diff。摘要按路径排序，每个文件保留路径、变更类型、增删统计和有界 patch；省略内容时明确标 truncated，不能暗示模型已读完。

Planner 输入包含完整 review_paths、context_paths、过滤计数、SemanticBrief、Anatomy clusters、config.hints 和目标维度数。静态 Prompt 放 system_prompt，动态内容序列化为 JSON 并放入不可信数据块。标题或源码中的 XML/Markdown 分隔符不改变工具权限。

工具通过 build_review_tools(repo_path=..., head_commit=..., snapshot=..., config=...) 构造，绑定同一个 snapshot。allowlist 恰好四个读取工具；RuntimeBridge 自己加入动态 FinalizeReview。

Planner Prompt 必须说明：任务是划分调查工作，不是预先找 N 个缺陷。review_prompt 应包含调查行为、比较契约、失败后果和停止条件。照 Plan 的正例和反例编写提示词夹具；测试验证内容和输入组装，不能把 fake 输出正确说成提示词效果已经证明。

## 7. Plan Repair 的确定性步骤

按以下顺序实现，不要边修复边调用模型：

1. 用排序后的 snapshot.review_paths 建立稳定文件顺序。去除不存在、绝对、越界、非 review 的 target。
2. 按模型 dimensions 原顺序处理。某路径第一次出现的 dimension 获得 owner，后续重复删除。不要为了 hash 稳定重排模型建议并改变“第一次优先”。
3. context 保留合法固定 head 路径，移除本 dimension target 交集，排序去重；不能绕过 secret 过滤。
4. 去除空 dimension。重复 name 用稳定后缀重命名。名字截断仍须保留后缀和唯一性。
5. 将所有尚未拥有 owner 的 review 文件合成 fallback dimension，代码提供通用任务书；没有遗漏就不创建空 fallback。
6. 按路径顺序拆分超过 max_files_per_work_item 的组。token 容量采用传入的确定性估算与已配置输入预算；若当前没有可用 token 预算，至少实施文件数和模型上下文检查，不能声称存在未实现的 token 硬限制。
7. 按 Plan 排序键从尾部尝试合并相邻组，只合并满足文件数及已有容量限制的组合。合并后不再拆分，避免循环。
8. 仍超出活动组上限时，将尾部组标记 deferred，保留其文件记录，写 unresolved_risks。max_final_dimensions 限制实际执行的组数；deferred 记录不消失。
9. hint 引用映射到拆分/合并后的名字。歧义无法消除或不足两个有效维度时丢弃 hint，记录 repair_actions。不要猜测模型想引用哪个重复名字。
10. 重新构造 ReviewPlan，校验每个 review 文件恰有一个 owner（可为 deferred），活动组没有超限。coverage_complete 表示所有文件实际被安排执行；有 deferred 时为 false。

示例：review 集合 a.py、b.py、c.py，模型组 A=[a.py,b.py]、B=[b.py]。B 去空后删除，c.py 进入 fallback；不能因 B 被删除而丢掉 c.py。

## 8. 失败与报告

Semantic JSON/schema/provider 调用失败可生成 fallback；CancelledError、整体 deadline 和 store 写失败必须继续传播，不能被当成 Semantic 降级。

Planner Harness 整体失败、始终无法合法终结时终止 run。Schema 合法但目标路径全无效，可以由 repair 补齐通用组；这与整体 schema 失败是不同情况。

report.completed_stage 扩展为 planning；增加 semantic、plan 两个可选业务字段，anatomy 输出时它们为空。增加 `agent_observations`。planning 成功后写阶段完成和 preparation_completed，不写最终 final_result。
