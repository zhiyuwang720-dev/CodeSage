# Spec 25.5A：内聚维度的 Plan Repair 与 Reviewer 输入

状态：已实施。适用范围：Plan25 的 25.4 Plan Repair 与 25.5 Reviewer 之间。本文修订这两个包中“每个文件恰好一个维度 owner”的旧约束；未提及的运行、工具及 Finding 契约继续按原 Spec 执行。

## 1. 背景与问题

Linera 真实运行 `4191586557c2` 的 Planner Draft 有七个调查维度。`grace-period-plumbing` 明确要求检查新参数的负值、NaN、超大值与 `mul_f64` 风险，但其唯一 target `updater.rs` 已被较早的 `quorum-loop-semantics` 占有。原 repair 删除重复 target，再删除空维度，使 Reviewer 从未收到这项调查。其余多个维度及三个 cross-reference hint 也被删除。最终报告的 `coverage_complete=true` 只证明四个文件都分配了 owner，不能证明调查问题得到了保留。

原 Draft 的 `quorum-loop-semantics` 还给出了一个不成立的场景：已达到 quorum，却声称 `highest_key_score + remaining_votes < quorum_threshold` 可以成立。剩余票数非负时，该场景与条件矛盾。Reviewer 沿着这个例子提交了错误的高严重度候选。

本轮目标是保留内聚的跨文件调查、减少重复 Reviewer、让调查问题可追溯，并阻止 Planner 把未经证明的反例写成 Reviewer 的预设结论。不增加模型调用阶段，不修改用户手工维护的三份 Reviewer 提示词。

## 2. 冻结的语义

- `target_files` 表示一个维度需要共同判断的变更文件；不同维度可以有交集。一个 Finding 的主位置仍须属于**当前维度**的 target。
- `context_files` 是只读支持文件，可包含另一维度的 target；自身 target 不重复出现在 context。
- 覆盖条件改为：所有未延期维度的 target 并集包含每个 review 文件，且没有待处理的延期调查。重复 target 本身不是错误。
- 一个维度保留一个稳定的 `name`。并入其他维度的名称不拼接到这个 name；各原始名称通过 `dimension_name_map` 映射到最终名称。
- 每个被保留的调查问题都带来源名称，按优先级与 Draft 原始位置稳定排序。Reviewer 一次 Harness 调用接收编号后的问题列表，不为每个问题额外启动 Agent。
- 仅在后续维度的合法 target 集合被某个已保留维度完整包含时，才做单向合并。非包含的维度完整保留；绝不将较早维度反向并入较晚的超集。

## 3. Repair 算法

### 3.1 输入规范化和排序

先固定 `review_paths` 的路径顺序。按 Draft 原始位置为重名维度生成稳定唯一名称；原始重名让按名称编写的 cross-reference hint 失去唯一指向，必须记录诊断并拒绝该 hint。逐维度去除非法、非 review、重复的 target 路径，并过滤非法或 secret context 路径。维度自身 target 非空后，按 `(priority 从小到大, Draft 原始位置)` 处理。

不能以 Draft 列表顺序代替 priority。Linera 原始列表的 priority 依次为 `1、3、2、4、6、5、7`。

### 3.2 完整包含时合并

对当前维度 D，寻找已保留维度 E，满足 `D.target_files ⊆ E.target_files`。若有多个候选，选择排序后最早保留的 E（优先级更高，原始位置更前）。不额外猜测哪个维度的语义“更接近”；稳定性优先。

将 D 的调查问题作为独立条目追加到 E 的问题列表；保留 D 原始名称、priority 和 rationale 以供报告追溯。E 的 `name`、target 和 priority 不改变。E 的 context 取两者合法 context 的去重并集，再排除 E 的 target。设置 `dimension_name_map[D.name] = [E.name]`，记录 `merged_contained_dimension` repair action，不再为 D 启动 Reviewer。

不直接把两个 prompt 拼成一段自由文本，也不截断后一个问题。修复后的 Plan 保存有序调查条目；Reviewer 输入构造时才把条目渲染为一段编号文本，仍使用原有一次 Harness 调用。

### 3.3 非包含时保留

若找不到完整包含 D 的已保留维度，原样保留 D 的完整 target 集合，即使它与其他维度部分重叠。例如：

| 已保留 | 后续 | 处理 |
|---|---|---|
| `{A,B}` | `{A}` | 将后续问题并入 `{A,B}`；只运行一个 Reviewer |
| `{A}` | `{A,B}` | 保留两个维度，第二个仍判断 A 与 B |
| `{A,B}` | `{A,B,C}` | 保留两个维度，第二个仍共同判断 A、B、C |

这会增加重叠文件的读取及候选重复概率，但保留跨文件问题本身的内聚性。现有 Candidate 收集允许不同维度对同一文件提交候选；后续 Cross/确定性去重处理语义重复。当前阶段记录维度数和候选来源，不把重复文件计为覆盖失败。

### 3.4 原有容量规则

保留现有“超过 `max_files_per_work_item` 的三分之一余量才拆分”规则。它仅作用于单个超大维度，与重叠 target 的包含判断无关；拆分的每个部分保留完整调查条目并记录同一原始维度的一对多名称映射。

`max_final_dimensions` 为硬上限。若仍超过上限，按优先级延期**完整维度**并记录 `unresolved_risks`；不得为了凑数量把两个不满足完整包含关系的维度任意拼在一起，也不得截断调查文本。延期维度留在报告中，但不启动 Reviewer，`coverage_complete=false`。

若 Draft 没覆盖某个 review 文件，按原有规则创建 fallback 维度。最终检查所有 review 文件至少出现在某个维度中；当前正在执行的维度若未覆盖所有文件，或存在延期维度，都不得宣称调查覆盖完整。

## 4. 名称、来源与 cross-reference hint

合并 `{A}` 维度 `grace-period-plumbing` 到 `quorum-loop-semantics` 后，最终名称仍为 `quorum-loop-semantics`。报告中的映射为：

```json
{
  "quorum-loop-semantics": ["quorum-loop-semantics"],
  "grace-period-plumbing": ["quorum-loop-semantics"]
}
```

使用列表值是因为一个超大维度仍可能依容量规则拆成两个最终维度。名称映射记录在 `ReviewPlan` 中；每条 Reviewer 调查也记录其来源名称。不要生成 `quorum-loop-semantics+grace-period-plumbing` 之类的长名称。

原 hint `dimension_names=["grace-period-plumbing", "caller-migration"]` 经映射变为 `["quorum-loop-semantics", "caller-migration"]`，relation 与 symbol 保留。若两个来源最终映射到同一维度，这已不是跨维度关系：将 relation 和 symbol 作为该维度的一个内部调查条目，移除这条 cross hint。若一个来源拆成多个最终维度、原始名称重名或指向延期维度，则不能唯一重映射；记录明确的 repair action 和未解决风险，不暗中宣称 hint 已处理。完全相同的最终 hint 去重。

目前 `cross_reference_hints` 只在 Plan/报告中持久化，Cross 阶段尚未实现消费；本轮不新增 Cross 调用。名称映射仍应正确，以免下一阶段接入时使用已不存在的维度名。

## 5. Reviewer 输入

`ReviewDimension` 业务模型保存有序调查条目，每条包含 `source_dimension`、`review_prompt`、`priority`、`rationale`。Reviewer 输入构造把它们格式化成一个 `review_prompt` 文本字段：

```text
Investigations for this dimension (in priority order):
1. [quorum-loop-semantics] Verify ...
2. [grace-period-plumbing] Check negative and NaN grace_period ...
```

维度自身的 target、context、priority、fallback 字段仍单独传入现有固定 JSON 区块。只有一个调查条目时，保留原始 prompt 文本，不额外包装。所有文本仍是待验证的 Planner 线索，Reviewer 必须以固定 head 的源码与 diff 作判断。三份 Reviewer prompt 文件不在本轮修改范围。

## 6. Planner 假设的低成本纠偏

在 Planner system prompt 中明确：Plan 分配调查问题，不能把一个未证明的执行轨迹写成成立的示例。涉及分支可达性时，应让 Reviewer 检查前置条件和状态不变量，再给出满足全部条件的具体轨迹或不可达证明。例如对 Linera，应询问“已达到 quorum 与 no-quorum break 条件是否可能同时成立”，而不预设两者可同时成立。

Planner 仍应优先生成内聚且少量的维度，同一文件的不同问题优先放在一个维度；若跨文件关系本身是独立调查单元，可以保留重叠 target。repair 是确定性兜底，不增加一次模型校验调用，也不尝试构建通用的源码逻辑证明器。

## 7. 代码影响与验收

| 位置 | 变化 |
|---|---|
| `schemas/pipeline.py` | 调查条目模型、最终维度条目列表、Plan 名称映射 |
| `services/plan_repair.py` | priority 稳定排序、完整包含合并、非包含重叠保留、context 合并、延期、hint 重映射 |
| `services/output_formatter.py` | 将调查条目编号传给现有 Reviewer 用户模板 |
| `prompts/planner.md` | 中立分支调查、不预设可达反例、允许有根据的维度重叠 |
| `prompts/planner_user.md` | 将唯一 owner 白名单改为完整覆盖白名单，并提醒核验分支可达性 |
| `tests/deep_review` | repair、Reviewer 输入、hint 映射、Linera Draft 回归测试 |

验收至少覆盖：`{A,B}+{A}` 合并；`{A}+{A,B}` 与 `{A,B}+{A,B,C}` 原样保留；priority 原始顺序乱序仍稳定；多个可包含目标时选优先级最高的先前维度；context 去重；名称不拼接且映射稳定；hint 重映射、内部化与不可唯一映射诊断；拆分与延期不静默丢调查；Linera 的负值/NaN 问题实际出现在 Reviewer 输入；`coverage_complete` 不再错误地要求 target 互斥。运行 Deep Review 相关回归测试，并保持用户手工修改的 Reviewer prompt 文件不变。
