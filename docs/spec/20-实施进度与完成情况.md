### 0.6 本轮规格偏差与已知缺口（必须知悉）

| 项 | 事实 | 处置 |
|---|---|---|
| SDK 重试所有者 | P05 表述为「独立调用由 LiteLLM SDK 重试」；实测 SDK 无法在不牺牲可观测/可断言的前提下约束底层重试 | 单一所有者：客户端 `num_retries=0` + 独立调用客户端有界 3 次；Harness 由 QueryLoop 负责（1 次实际请求）。已写入 `retry-budget.json` 并标注偏差原因 |
| OpenAI 兼容前缀 | LiteLLM 1.98 的 `deepseek/` 流路径把 HTTP chunk 边界当 SSE 行读取，抛 `'int' object has no attribute 'get'`，截断流被伪装成正常结束 | OpenAI Chat 兼容族统一 `openai/<model>` + `api_base`（wire 协议本就是 OpenAI 兼容）。已记入能力矩阵 G-01 |
| usage 尾块 | LiteLLM 1.98 在结束块**之后**才交付合并 usage chunk | 客户端在结束块后限时读取尾块（`TAIL_METADATA_TIMEOUT_SECONDS=2`）。G-02 |
| 流截断检测 | 网关显式 `Connection: close` 时 SDK 把截断当正常 EOF | 「流结束但从未观测到结束块」→ 显式 `error(stream_truncated)`；显式 close 场景退化为 done + `dropped_incomplete_tool_calls`。残余缺口 G-03 |
| 并发回调 | 并发 dispatch 下 SDK 可能丢失部分 success callback | 请求/配置/认证隔离不受影响；顺序调用回调完整。G-04 |
| usage 合成零 | SDK 在 wire 缺 usage 时合成全零/估算 usage | 统一 `zero_fidelity=unverified`；用「非零 total 佐证」用例区分真实 0 |
| prompt_cache/tokenizer/memory_compressor | 直接/相对引用检索：仅被已删除模块与 `models/__init__` 重导出引用 | 全部删除，无隐蔽旧路径 |

## 2. 状态规则

需求/工作包状态只能使用：

| 状态 | 条件 |
|---|---|
| not_started | 尚未开始 |
| in_progress | 有正在进行的代码/测试工作 |
| implemented | 代码与对应测试已写，尚缺成功执行证据 |
| verified | 所需级别测试通过且证据可追溯到当前实现 |
| blocked | 具体外部/环境/信息阻塞，写原因及解除条件 |
| retest_required | 相关代码/配置改变，历史PASS不再代表当前版本 |

总体状态：not_started → in_progress → engineering_verified → real_verified → completed。engineering_verified表示自动验收全部通过，不能简称计划完成；completed要求全部证据、真实验收、文档与最后commit一致。

需求不得用N/A免验。未启用provider能力可以unverified列在能力矩阵，但真实DeepSeek主路径不能跳过。需求范围改变必须记录规格版本、理由和替代验收，不允许改成“以后再做”后仍宣称完成。
