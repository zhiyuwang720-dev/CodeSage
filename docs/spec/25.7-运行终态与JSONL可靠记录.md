# Spec 25.7：运行终态与 JSONL 可靠记录

版本：1.0。状态：待实施。依赖：25.6 已能用 fake runtime 完成 final。
关联：[Plan25](../plan/25-CodeSageDeep-V1核心移植与原型闭环.md) 第 8、9 节；[总索引](25-CodeSageDeep-V1核心移植与原型闭环.md)。

## 1. 阶段目标

本包把已连接的各阶段收敛成可以解释成功、部分成功、失败和取消的完整运行。重点是终态计算、usage 汇总、并行任务结束、JSONL 写入顺序和最终文件发布。

不是重新创建 orchestrator。完成后，一次运行的最后完成阶段、每个 Reviewer 的成功与失败、用量缺失和最终结果都可以从领域日志与关联 session 定位。

## 2. 文件影响范围

| 文件 | 工作 |
|---|---|
| services/orchestrator.py | 统一失败/取消/timeout，计算终态与 metrics |
| services/service.py | 整体期限、任务收尾和统一返回边界 |
| storage/protocol.py | 保留 append-only Port，不扩成会话数据库接口 |
| storage/jsonl_repository.py | sequence、flush、错误传播和结果物化 |
| schemas/output.py | metrics、最终结果必要字段约束 |
| services/output_formatter.py | 稳定业务序列化、脱敏输出 |
| tests/deep_review/test_jsonl_repository.py | 截断/失败/序列测试 |
| tests/deep_review/test_orchestrator.py | 终态矩阵与并发取消 |

只有具体 storage 实现知道 JSONL 文件位置。orchestrator 不直接调用 open 或 Path.write_text。默认 store 在 append(final_result) 时物化 result.json；memory store 只记录事件，不需要文件系统。

## 3. 状态计算表

终态由确定性函数统一计算，不允许各阶段直接随意覆盖结果.status。优先级为 failed 高于 partial，高于 completed。取消用 run_cancelled 记录并继续抛出 CancelledError；不强行塞进只有三态的 DeepReviewResult。

| 条件 | 结果 |
|---|---|
| 输入、配置无效 | CLI 退出 2；若 run 已创建则记录失败 |
| Planner 整体失败、全部实际 Reviewer 失败、收尾失败、存储失败 | failed |
| 部分 Reviewer 失败、deferred 文件、Cross fallback、有效结果被业务校验丢弃 | partial |
| Evidence 缺失影响验证、Cross 漏项补 keep/空 drop 修复 | partial |
| 仅 Semantic fallback、Plan 漏项已完整补齐且后续成功 | 可 completed，保留 degraded 诊断 |
| 正常审查后零 Finding | completed |
| review_paths 为空，无需执行 Reviewer | completed，summary 说明无可审查文件 |
| 进程被直接终止 | 不伪造终态；日志最后完整事件是诊断边界 |

“全部 Reviewer 失败”只在确有至少一个活动 Reviewer 且全部失败时成立。只有 deferred 文件而无活动组时应明确 partial/无实际审查，不能误报成功。

单次 Evidence 空值未必是异常，例如没有 caller。只有提取失败或缺少必要 primary/diff 证据才列为验证缺失；不要把所有空可选字段都判 partial。

## 4. 事件记录格式与生产者

每行 envelope 包含 schema_version=1、sequence、timestamp、run_id、record_type、payload。sequence 从 1 开始，单调递增；timestamp 为 UTC ISO-8601。duration 使用 monotonic 计算，不能用墙钟差值。

事件至少覆盖：

- run_started，记录固定配置摘要与输入身份。
- stage_started/stage_completed/stage_failed，记录实际阶段。
- input_loaded/filter_completed，记录允许文件计数、commit 和过滤原因计数。
- semantic_completed/semantic_fallback。
- plan_completed/plan_repaired；不再使用容易误解为 Planner 整体 fallback 的 plan_fallback。
- reviewer_completed/reviewer_failed，含 dimension、session 和用量。
- evidence_completed，含缺失数量和原因。
- cross_analysis_completed/cross_analysis_fallback/cross_skipped。
- preparation_completed 或 final_result；运行失败时 run_failed；取消时 run_cancelled。

并行 Reviewer 在协程里积累结果，由 orchestrator gather 后按 Plan 顺序写完成事件。因此 JSONL 的 Reviewer 结果顺序稳定，但不能宣称完成事件实时反映实际完成先后。真实开始/结束时间可以放在 payload，sequence 表示写入顺序。

为诊断中途崩溃，在 fan-out 前写 reviewer_batch_started，列出计划执行的维度。取消时收集已经完成的结果并稳定记录后再写取消事件。不要等所有任务成功才留下任何 Reviewer 相关记录。

## 5. usage 与 cost 汇总

每次 AgentCallResult 保存本次可获得的 usage、session_id、cost_usd。session 来自 Runtime，不能用 deep-review run_id 冒充 session id。

计数必须分清两个层次：阶段调用拓扑是 1 AI + Planner + W Reviewer + Cross；Harness 内有多轮 provider 请求。当前若无法可靠统计 provider request count，metrics.model_calls 应明确记录阶段调用数，并在报告中命名解释，不能拿它与 OCR 的 HTTP 请求数直接比较。

token 汇总要求：

1. 累加每次调用实际报告的输入、输出和总 token。
2. 任意调用缺用量、失败请求用量不可得，usage_complete=false。
3. input/output 缺失时保留 None；不得用 0 表示未知。
4. 若现有 total_tokens 保留整数默认值，则它表示已知用量之和，必须配合 usage_complete=false；报告不能显示成精确总成本。
5. 不重复累加 HarnessResult.usage 和同一 session 的底层模型 usage。
6. cost 仅在所有调用均有可信成本时给精确总 cost；否则 cost_usd=None、cost_available=false。
7. 缓存 token 的供应商口径可能不同，保留原始摘要，禁止未经证明从 input_tokens 再减一次 cached_tokens。

duration_ms 为整个 run 墙钟耗时。并行 Reviewer duration 相加不等于总墙钟耗时，报告中必须分开呈现。

## 6. JSONL 与 result.json 写入

append 前完成 JSON 序列化和脱敏。每条记录一次追加并 flush；不要宣传跨进程原子性或断电持久性。当前只支持同一 run 单 writer，不增加全局文件锁服务。

具体 store 收到 final_result 时：

1. 把结果序列化到同目录临时文件并 flush，确保目标 JSON 完整可解析。
2. 追加 final_result 事件并 flush，作为领域日志中的最终结果记录。
3. 使用 os.replace 将临时结果替换为 result.json。
4. 任一步失败向上传播。若事件已有但 result 文件尚未发布，记录可诊断的不一致，CLI 返回非零；不得开始恢复或重跑模型来修补。

result.json 是日志结果的物化副本。进程被杀可能留下临时文件或完整事件但没有 result.json；这是 V1 允许且需要报告的边界。新 run 不读取这些文件继续执行。

run_failed 尽力写一次。若 store 本身不可写，向 stderr 给出短错误并结束，不无限尝试写“写失败事件”。--output 额外导出文件失败也必须返回非零，不能吞掉导出失败。

## 7. 超时和取消实施步骤

从 run 开始建立单一 deadline，默认 config.max_duration_seconds=1800。各阶段不能各自重新获得 1800 秒。同步 subprocess 的已有 timeout 仍要保留；取消 to_thread 不会自动终止其中的 subprocess，这一事实必须在测试/交付说明中写清。

Reviewer 创建的 asyncio.Task 全部登记并在 finally 回收。整体超时记录 run_failed(reason=timeout)；用户取消记录 run_cancelled 并继续传播。任务停止后不得再发起 Cross 或新的 provider 请求。

V1 只能尽力中止已经发出的 provider 请求，不能保证供应商停止计费。不得为了实现完美远端取消去重构共享 Runtime。若共享 Runtime 吞掉取消或后台持续请求，应作为阻塞缺陷单独修复并测试。

## 8. 红线

不新增 stage resume、lease/fencing、SQL 领域表、runtime session JSONL 实现。不写完整 prompt/transcript/源码/环境变量；Finding 自身有界的证据文本可以作为业务输出保留，但必须脱敏。

稳定 hash 不包含 sequence/timestamp/run_id/usage；完整事件字节在不同运行间不要求相同。可审计指保存阶段和结果来源，不等于保存模型隐藏推理。

## 9. 测试用例

| 编号 | 故障注入/场景 | 验收断言 |
|---|---|---|
| L01 | 正常完整 fake run | 有唯一 final_result；result.json 可校验 |
| L02 | Semantic fallback，其余成功 | completed + degraded 诊断 |
| L03 | deferred 或单 Reviewer 失败 | partial，成功 Findings 保留 |
| L04 | 全部 Reviewer 失败 | failed，无 Cross 调用 |
| L05 | JSONL 第 N 次写失败 | 非零退出，无伪造成功；不无限重试 |
| L06 | 多次 append | sequence 连续、各完整行可解析 |
| L07 | 手工截断最后一行 | 诊断工具可读取前面完整行；不会启动 resume |
| L08 | result 临时文件写入/replace 失败 | 明确失败，保留可诊断记录 |
| L09 | 3 组乱序完成 | 完成事件稳定排序，duration 保留实际值 |
| L10 | deadline 在并行阶段到期 | 所有已登记任务回收；无 Cross |
| L11 | provider 用量缺一项 | usage_complete=false，不伪造完整总量 |
| L12 | Harness 汇总与底层 usage 同时存在 | 不重复计数 |
| L13 | cost 缺失 | None/false，而不是 0 美元 |
| L14 | 注入看似 API key 的 provider 错误 | 日志不出现密钥原文 |
| L15 | 同一输入再次执行 | 新目录、新 session；不读旧事件复用结果 |
| L16 | 零 review 文件 | 合法空最终结果，零 Reviewer |
