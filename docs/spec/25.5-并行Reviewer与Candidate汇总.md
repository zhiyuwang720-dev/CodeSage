# Spec 25.5：并行 Reviewer 与 Candidate 汇总

版本：1.0。状态：待实施。依赖：25.4 的 repaired ReviewPlan 已可从 run 产生。
关联：[Plan25](../plan/25-CodeSageDeep-V1核心移植与原型闭环.md) 5.4、6.7、6.8；[总索引](25-CodeSageDeep-V1核心移植与原型闭环.md)。

## 1. 阶段目标

对每个非 deferred dimension 执行一次独立 Reviewer Harness。各 Reviewer 调用同一角色实现，调查内容来自 dimension.review_prompt。汇总成功结果后生成稳定 Candidate 列表，给下一包 Evidence/Cross 使用。

本包必须将 --through review 接入现有 run。报告是开发阶段报告，pipeline_complete=false。报告中明确成功、失败和延期的 dimension；不能以 findings 为空判断审查失败。

## 3. 模型输出与映射规则

ReviewerResultDraft 只含 findings 和 summary。ReviewFindingDraft 字段为 file_path、line_start、line_end、severity、title、body、evidence、suggestion、confidence、tags。字段说明和基本约束按 Plan 5.4；模型不能填写 dimension_name、source 或运行 ID。

findings 允许为空。不设置最低数量，也不因某个角色名称推导必须返回的问题类型。Plan 中每次响应最多 32 项是结构输出保护，不能在 Python 中偷偷切片；Schema 拒绝超限输出后由原 Harness 终结纠错。若仍不能合法终结，记录失败。不能称“保留了全部问题”而省略超限诊断。

Agent 在本地把 Draft dump 交给 reviewer_result_mapper，并传入当前 dimension、snapshot、固定 head 行数查询能力。mapper 不 import Agent Draft，不直接访问 SQL。

逐条映射过程：

1. 规范化 file_path，并确认属于当前 dimension.target_files，而不是仅存在于仓库。
2. 确认固定 head 中该路径是可读普通文件。已删除路径不能成为新代码侧 Finding 主位置。
3. start/end 都为 None 时允许文件级 Finding；只有 start 时令 end=start；只有 end 时判非法；都有值时要求 1 <= start <= end <= head 行数。
4. 对合法项逐字段构造业务 ReviewFinding，由代码填写 dimension_name 和 source=reviewer。
5. 非法条目丢弃并记录原因。不得夹紧越界行号来把错误位置伪装成合法位置。
6. 所有项被丢弃时仍区分“模型合法返回零项”和“输出映射全部失败”：后者必须标记该维度降级，最终可用性在 25.7 判为 partial。

行号校验使用固定 commit，不从工作区读取。跨文件调查允许读取 context 和调用者，但报告主位置必须属于自己的 target；最终跨维度风险由 Cross 处理。

## 4. 输入与 Prompt 的具体要求

每个 Reviewer 输入包含完整 target 列表、context 列表、dimension.review_prompt、SemanticBrief 摘要和 target 的 diff。共享静态角色 Prompt 放前面，动态数据放后面。不要把其他 Reviewer 的 transcript 或尚未验证的结果放进来。

普通 Prompt 需要逐项说明：

- 追踪任务书中的具体行为与契约，必要时读取调用者或消费者。
- 只报告由本次变更引入或暴露、可触发、值得作者修复的问题。
- 先寻找已有 guard、错误处理和类型约束，避免只凭局部片段下结论。
- 说明触发条件、失败机制、实际后果和代码证据。
- 零 Finding 是合法结论，禁止为每文件或每维度凑数量。
- 只能使用四工具和 FinalizeReview，不能启动子审计。

fallback Prompt 覆盖 correctness/security/architecture/quality 的通用调查，但也要限定在 target 变更。即使一个 merged dimension 同时包含模型组和 fallback 文件，也使用 fallback=True 的通用规则并保留已有任务线索。

## 5. 并行编排实施步骤

1. 将 plan.dimensions 中非 deferred 的组按最终 Plan 顺序编号；该顺序决定汇总顺序。
2. 在 service/run 所有 Reviewer 共用的层级创建一个 asyncio.Semaphore(config.max_concurrent_reviewers)。不要每组各建一个 semaphore。若同一 service 允许并发 run，该 service 的 Reviewer 共用该 semaphore。
3. 每个协程在获取 semaphore 后调用一次 Reviewer Harness，使用 max_turns_reviewer 和独立 runtime session。
4. 协程返回 AgentCallResult[ReviewerResult] 与本地诊断；不直接 append JSONL。
5. gather 后按 Plan 顺序处理结果。单组失败保留其他组，全部实际执行组失败则 run failed。
6. 有成功空结果的组属于成功，不计作失败；无 review 文件时跳过模型，不制造“全部失败”。
7. 取消或 deadline 到期时 cancel 尚未完成的任务，并 await 回收。不得让后台 Reviewer 在 run 结束后继续调用模型。
8. 串行写 reviewer_completed/reviewer_failed，然后生成 Candidate 列表。

semaphore 只限制同时在运行的 Harness 数。W 表示实际启动的非 deferred Reviewer 数；总 provider 请求数可能更多，不能用 W 冒充模型 HTTP 请求次数。

## 6. Candidate 汇总契约

固定排序键是 dimension_order、file_path、line_start、severity_rank、title。None 行号使用统一哨兵 0；severity_rank 按 critical/high/medium/low 排列。以上字段相同时，使用规范化完整 Finding JSON 作为最终 tie-break，避免不同完成顺序造成不稳定。

排序后 enumerate 生成仅本次 Cross 请求使用的 0-based index。业务 ReviewFinding 和最终输出都不增加永久 candidate ID。EvidencePackage 中允许使用该临时 index。

确定性摘要包含每一条 Candidate 的编号、位置、severity、title、body/claim、evidence 和 dimension_name。body/evidence 若截断必须标记，Candidate 本身保持完整。此时不做语义去重、不先删低严重度 Candidate。最终去重在 25.6。

## 7. 技术红线与失败边界

不实现固定三角色 fan-out，不给各组配一套不同模型类。不新增独立 worthiness 模型调用，不在 Reviewer 失败后启动补偿 Reviewer。不共享可变对话历史，不在公共业务模型中包含 Draft。

单 Reviewer 的普通调用异常由 AgentCallResult 包装；CancelledError、存储失败和全局超时向外传播。原始错误可保存脱敏类型和短消息，禁止落盘完整 provider 请求体。

## 8. 测试用例设计

| 编号 | 夹具/操作 | 预期 |
|---|---|---|
| R01 | 6 个组、并发上限 2，fake 用事件阻塞 | 同时进入 Harness 的峰值为 2 |
| R02 | 前组慢、后组快 | Candidate 顺序仍按 Plan；JSONL 汇总顺序稳定 |
| R03 | 一组失败，两组成功 | 两组 Finding 保留，失败维度有记录 |
| R04 | 所有执行组失败 | run failed，不进入 Cross |
| R05 | 成功返回空 findings | 成功计数增加，不按失败处理 |
| R06 | 一个 deferred 组 | 无 Harness 调用；未审路径保留 |
| R07 | head 10 行，输出 11 行或反向区间 | 丢弃并记录原因，不夹紧行号 |
| R08 | 输出 context-only 路径 | mapper 拒绝主位置 |
| R09 | 文件级 Finding，start/end=None | 合法保留 |
| R10 | 取消正在等待和执行的任务 | 所有任务回收；semaphore 释放；无新调用 |
| R11 | 重排完成顺序和等键 Finding | Candidate 内容与编号稳定 |
| R12 | fake review CLI | 实际经历 Anatomy→Semantic→Plan→Reviewer |
| R13 | fallback 组 | 使用 fallback Prompt；四工具仍受固定 head 约束 |
| R14 | 每次 schema 字段检查 | description 齐全；无 dimension_name/source 输入字段 |
