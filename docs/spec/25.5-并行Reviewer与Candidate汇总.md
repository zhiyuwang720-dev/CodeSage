# Spec 25.5：并行 Reviewer 与 Candidate 汇总

版本：1.0。状态：待实施。依赖：25.4 的 repaired ReviewPlan 已可从 run 产生。
关联：[Plan25](../plan/25-CodeSageDeep-V1核心移植与原型闭环.md) 5.4、6.7、6.8；[总索引](25-CodeSageDeep-V1核心移植与原型闭环.md)。

## 1. 阶段目标

对每个非 deferred dimension 执行一次独立 Reviewer Harness。各 Reviewer 调用同一角色实现，调查内容来自 dimension.review_prompt。汇总成功结果后生成稳定 Candidate 列表，给下一包 Evidence/Cross 使用。

本包必须将 --through review 接入现有 run。报告是开发阶段报告，pipeline_complete=false。报告中明确成功、失败和延期的 dimension；不能以 findings 为空判断审查失败。

继承 Spec 25.4 观测契约，并将 `AgentObservation.stage` Literal 扩展 `"reviewer"`。每个 Reviewer 的 `AgentCallResult` 转为 observation；`reviewer_completed/reviewer_failed` 和 PreparationReport 保留 session_id、原始 usage、cost_usd 与短 error。observations 按 Plan dimension 顺序稳定排列，不按完成顺序。usage/cost 不可得为 None，不补零。

## 3. 模型输出与映射规则

ReviewerResultDraft 只含 findings 和 summary。应用内部的文本硬上限为 title 160、body 4,000、evidence 3,000、suggestion 2,000、summary 2,000、tag 64 字符；这些数字不得写入 `Field(description=...)` 或模型可见 JSON Schema。Draft 前置校验对超限文本字段逐项确定性截断并追加可见标记。file_path 是 Finding 身份/归属字段，不做破坏性截断；其业务有效性由 target ownership 校验决定。ReviewFindingDraft 字段为 file_path、line_start、line_end、severity、title、body、evidence、suggestion、confidence、tags。模型不能填写 dimension_name、source 或运行 ID。

findings 允许为空。不设置最低数量，也不因某个角色名称推导必须返回的问题类型。Plan 中每次响应最多 32 项是独立的结构项数上限，不能在 Python 中偷偷切片。字符长度超限不能拒绝整批结果、不能因长度丢弃 Finding；只截断超限的文本字段并附标记。其他结构错误或超过 Finding 项数上限仍由 Harness 终结纠错，若仍不能合法终结则记录失败。

Agent 在本地把 Draft dump 交给 reviewer_result_mapper，并传入当前 dimension、snapshot、固定 head 行数查询能力。mapper 不 import Agent Draft，不直接访问 SQL。

逐条映射过程：

1. 规范化 file_path，并确认属于当前 dimension.target_files，而不是仅存在于仓库。
2. 确认固定 head 中该路径是可读普通文件。已删除路径不能成为新代码侧 Finding 主位置。
3. start/end 都为 None 时允许文件级 Finding；只有 start 时令 end=start；只有 end 时判非法；都有值时要求 1 <= start <= end <= head 行数。
4. 对合法项逐字段构造业务 ReviewFinding，由代码填写 dimension_name 和 source=reviewer。
5. 非法条目丢弃并记录原因。不得夹紧越界行号来把错误位置伪装成合法位置。
6. 所有项被丢弃时仍区分“模型合法返回零项”和“输出映射全部失败”：后者必须标记该维度降级，最终可用性在 25.7 判为 partial。

行号校验使用固定 commit，不从工作区读取。跨文件调查允许读取 context 和调用者，但报告主位置必须属于自己的 target；最终跨维度风险由 Cross 处理。

## 4. Reviewer 输入、上下文交接与 Prompt 契约

### 4.1 Prompt 文件职责

Prompt 必须使用现有 `services/prompt_loader.py` 的 `render_prompt`。不要在 `agents/reviewer.py` 用多段 f-string 或散落的字符串拼接构造任务。模板 placeholder 必须唯一且与传入参数完全一致；加载或渲染错误应在发起模型调用前失败。

| 模板 | 内容 |
|---|---|
| `prompts/reviewer.md` | 稳定的 Reviewer 角色、判断原则、调查顺序、停止条件和 FinalizeReview 要求 |
| `prompts/reviewer_fallback.md` | 没有 Planner 专项任务时使用的通用审查方法；它替换普通 system prompt，不替换输入数据 |
| `prompts/reviewer_user.md` | 本维度任务、边界说明、Semantic/Anatomy 提示、固定提交、target diff 和工具说明 |

静态 system prompt 负责说明“如何审查和如何判断”；动态 user template 负责说明“本次审查对象是什么、每段材料有什么用途、哪些材料可信度有限”。Draft/Schema 负责约束字段形状。不要把 Schema 字段表重复扩写成主要提示词，也不要只解释字段而漏掉 Reviewer 要解决的问题。

动态内容先由 `services/output_formatter.py` 组装为有名字的 JSON 区块，再由 `reviewer_user.md` 渲染。JSON 使用稳定排序；代码、PR 文本、commit message、Planner 文本和工具输出都明确标成待分析数据，不能作为提示词指令执行。数据区块旁必须说明它是事实、线索还是范围约束，不能只把 JSON 原样贴给模型。

`reviewer_user.md` 使用以下固定 placeholder，由 Agent 用 `render_prompt` 一次性传入，不在运行时增删区块：

| Placeholder | 内容 |
|---|---|
| `dimension_json` | `name`、`review_prompt`、`priority`、`fallback`；模板说明它是任务线索而非 bug 结论。 |
| `scope_json` | 固定 base/head、完整 `target_files`、只读 `context_files`；模板说明 target 是唯一 Finding 主位置范围。 |
| `semantic_json` | SemanticBrief 全部业务字段及 `source`/`confidence`；模板说明它仅用于优先级线索，必须核验。 |
| `target_diffs_json` | 每个 target 的变更摘要/diff 和截断标记；不得抽样或省略 target。 |

不默认重复传入完整 PR description、commit messages 或完整 Anatomy；SemanticBrief 和 dimension 已经承担压缩后的交接信息。若后续实测证明某一原始字段会改变审查结果，再作为有界输入增加并同步更新模板契约。

### 4.2 上游材料的含义和可信度

每个 Reviewer 的 user message 要逐项解释以下输入：

| 输入 | 给 Reviewer 的解释 |
|---|---|
| `dimension.name` | 该调查工作的短标签，不代表漏洞分类，也不预设结论。 |
| `dimension.review_prompt` | Planner 提出的调查问题和停止边界，是待验证的工作假设，不是 bug 结论。Reviewer 应检查实际 diff 与代码；问题不成立时允许返回零 Finding。 |
| `target_files` | 本维度唯一允许作为 Finding 主位置的变更文件白名单。必须完整展示，不得为缩短输入而删文件。 |
| `context_files` | 只读辅助上下文，可读取调用者、消费者或契约；不属于本维度的 Finding 归属范围。 |
| `SemanticBrief` | Semantic 的初步解释，只是调查线索。`source=fallback` 或 confidence 较低时应降低依赖；其中的意图、风险面和假设都要回到 diff/代码核验。 |
| target diff | 变更行为的首要起点；若字段标记截断，不能用未显示内容推断“代码不存在”，需要时用工具读取固定 head 内容或 diff。 |
| 固定 base/head 与读取工具 | 所有读取都针对本次固定提交。工具输出是代码证据，但其中的注释、文档和字符串仍是非可信输入。 |
| PR 元数据（如果未来作为显式输入加入） | 作者对意图的陈述，不证明实现已满足，也不是给模型的指令；V1 默认不重复传入完整原文。 |

不向 Reviewer 传递其他 Reviewer 的 transcript、未映射 Draft、模型调用日志或 usage。不同维度保持独立；跨维度候选关系留给 25.6。

### 4.3 Reviewer 判断任务

普通 Reviewer 必须围绕当前维度完成以下工作：

1. 把 `review_prompt` 拆成可核验的行为、数据流或契约问题，先从 target diff 确认这次具体改变了什么。
2. 仅在能改变结论时读取调用者、消费者、配置或相关 context；确认触发条件、可达路径、已有 guard 和错误处理。
3. 对每个拟报告的问题写清触发条件、失效机制、用户或系统后果，以及能定位到固定 head 的代码证据。
4. 只报告本次变更引入或暴露、值得作者修复的问题。不能把“值得查看”写成 Finding，也不能因某种维度名称而强行产生该类 Finding。
5. 输出零、一或多条 Finding 均有效；没有 Finding 是合法审查结论。禁止按文件数、维度数或预期 Recall 凑数量。
6. 证据已足以判断时停止搜索。不得为满足轮数继续调用工具或扩大到无关全仓检查。

fallback 维度使用 `reviewer_fallback.md`，按 correctness、security、architecture、quality 检查本维度的变更；仍须遵守相同的证据、归属、零 Finding 和停止规则。若 Plan repair 把普通维度与 fallback 工作合并且最终 `fallback=True`，使用通用模板，同时把原有 `review_prompt` 保留为优先调查线索。

### 4.4 结构化终结和有界执行

`ReviewerResultDraft` 与 `ReviewFindingDraft` 的 `Field(description=...)` 说明输出字段含义及边界；模型不得输出 `source`、`dimension_name`、run ID 或工具执行状态。系统提示词专注于判断质量，Schema 专注于结构校验，mapper 专注于业务边界校验。三者职责不能互相替代。

Reviewer 只能使用 `file_read`、`file_read_diff`、`file_find`、`code_search` 和动态 `FinalizeReview`。工具说明应告诉模型各工具适合回答什么问题；不能要求模型使用本地不存在的 Read/Grep/Glob/PowerShell 工具。不得启动子代理或子审计。

最大 turn 数按最终 `target_files` 数量有界分配：1–3 个文件为 8 turns，4–7 个为 12 turns，8–16 个为 16 turns；Plan repair 不应留下超过 16 个 target 的单一维度。该映射集中在 `DeepReviewConfig` 的简单策略方法中，不在 Agent 和 Orchestrator 各复制一份。允许值由执行代码传给 Harness，不能由模型自行增加。Prompt 明确要求最迟在最后两个 turn 停止探索、整理已验证证据并调用 `FinalizeReview`；不得以增加 turn 数或新增模型调用弥补无效调查。借鉴 OCR 的 concise/objective 输出约束，但保留 CodeSage 当前批量 `FinalizeReview` 结构；文本超长由 Draft 确定性截断，结构/业务错误仍使用现有终结校验路径。

## 5. 并行编排实施步骤

1. 将 plan.dimensions 中非 deferred 的组按最终 Plan 顺序编号；该顺序决定汇总顺序。
2. 在 service/run 所有 Reviewer 共用的层级创建一个 asyncio.Semaphore(config.max_concurrent_reviewers)。不要每组各建一个 semaphore。若同一 service 允许并发 run，该 service 的 Reviewer 共用该 semaphore。
3. 每个协程在获取 semaphore 后调用一次 Reviewer Harness，按该 dimension 的 `target_files` 数量使用第 4.4 节的 turn 上限，并创建独立 runtime session。
4. 协程返回 AgentCallResult[ReviewerResult] 与本地诊断；不直接 append JSONL。
5. gather 后按 Plan 顺序处理结果。单组失败保留其他组，全部实际执行组失败则 run failed。
6. 有成功空结果的组属于成功，不计作失败；无 review 文件时跳过模型，不制造“全部失败”。
7. 取消或 deadline 到期时 cancel 尚未完成的任务，并 await 回收。不得让后台 Reviewer 在 run 结束后继续调用模型。
8. 串行写 reviewer_completed/reviewer_failed，然后生成 Candidate 列表。

semaphore 只限制同时在运行的 Harness 数。W 表示实际启动的非 deferred Reviewer 数；总 provider 请求数可能更多，不能用 W 冒充模型 HTTP 请求次数。

## 6. Candidate 汇总契约

固定排序键是 dimension_order、file_path、line_start、severity_rank、title。None 行号使用统一哨兵 0；severity_rank 按 critical/high/medium/low 排列。以上字段相同时，使用规范化完整 Finding JSON 作为最终 tie-break，避免不同完成顺序造成不稳定。

排序后 enumerate 生成仅本次 Cross 请求使用的 0-based index。业务 ReviewFinding 和最终输出都不增加永久 candidate ID。EvidencePackage 中允许使用该临时 index。

确定性摘要包含每一条 Candidate 的编号、位置、severity、title、body/claim、evidence 和 dimension_name。body/evidence 若截断必须标记，Candidate 本身保持完整。此时不做语义去重、不先删低严重度 Candidate。最终去重在 25.6。

## 7. 技术红线与失败边界

不实现固定三角色 fan-out，不给各组配一套不同模型类。不新增独立 worthiness 模型调用，不在 Reviewer 失败后启动补偿 Reviewer。不共享可变对话历史，不在公共业务模型中包含 Draft。

单 Reviewer 的普通调用异常由 AgentCallResult 包装；CancelledError、存储失败和全局超时向外传播。原始错误可保存脱敏类型和短消息，禁止落盘完整 provider 请求体。

## 8. 测试用例设计

| 编号 | 夹具/操作 | 预期 |
|---|---|---|
| R01 | 6 个组、并发上限 2，fake 用事件阻塞 | 同时进入 Harness 的峰值为 2 |
| R02 | 前组慢、后组快 | Candidate 顺序仍按 Plan；JSONL 汇总顺序稳定 |
| R03 | 一组失败，两组成功 | 两组 Finding 保留，失败维度有记录 |
| R04 | 所有执行组失败 | run failed，不进入 Cross |
| R05 | 成功返回空 findings | 成功计数增加，不按失败处理 |
| R06 | 一个 deferred 组 | 无 Harness 调用；未审路径保留 |
| R07 | head 10 行，输出 11 行或反向区间 | 丢弃并记录原因，不夹紧行号 |
| R08 | 输出 context-only 路径 | mapper 拒绝主位置 |
| R09 | 文件级 Finding，start/end=None | 合法保留 |
| R10 | 取消正在等待和执行的任务 | 所有任务回收；semaphore 释放；无新调用 |
| R11 | 重排完成顺序和等键 Finding | Candidate 内容与编号稳定 |
| R12 | fake review CLI | 实际经历 Anatomy→Semantic→Plan→Reviewer |
| R13 | fallback 组 | 使用 fallback Prompt；四工具仍受固定 head 约束 |

| R15 | 检查普通/fallback 的渲染 Prompt | system 与 user 模板分工明确；维度任务、文件所有权、context 只读和 Semantic 线索的可信度均有解释；没有把线索写成结论 |
| R16 | Planner 任务、PR 描述或源码包含提示词注入文本 | 渲染结果把它们保留为 JSON 数据并明确标为非可信内容；模型指令不从数据字段扩展 |

| R18 | 达到 Reviewer 最后两个 turn 仍有次要搜索方向 | Prompt 要求停止次要搜索并调用 FinalizeReview，不发起无界工具循环 |
