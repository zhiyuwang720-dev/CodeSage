# Spec 25.5B：审查质量基线、Plan/Reviewer 提示词与终结兼容

状态：阶段 1–3 已实现并完成离线回归；真实模型与缓存效果仍须显式 opt-in 验证。本文不授权阶段 4 的 turn 上限调整。关联 [Plan25](../plan/25-CodeSageDeep-V1核心移植与原型闭环.md)、[Spec 25.4](25.4-Semantic与Planner及PlanRepair.md)、[Spec 25.5](25.5-并行Reviewer与Candidate汇总.md) 和 [Spec 25.5A](25.5A-PlanRepair内聚维度与Reviewer输入.md)。离线逐条基线见 [25.5B 三例 Review 质量基线](../analysis/25.5B-三例Review质量基线.md)。

## 0. 背景、优先级与覆盖关系

三个 AACR 用例的 Review 报告显示，低原始 Recall 不等于 Planner 完全没有提出相应调查。Linera 的 Plan 已包含 grace period 非有限值和错误字符串；mpv 的 Plan 已包含 RNG 边界、播种与调用方；Ollama 的 Plan 已包含 nil tensor、`Ints()` 和空 Outputs。然而 Ollama 的 13 条 Candidate 中出现了“已验证没有问题”一类非问题陈述，且会话中有搜索失败和工具超时。部分参考评论属于风格/文档意见，另有参考评论与固定 head 源码矛盾。不能仅通过放宽过滤、增加 turns 或让模型接触 Ground Truth 来提高数字。

本规格按以下顺序实施并分别验收：

1. 建立离线质量基线，明确原始参考评论与可行动问题的不同口径。
2. 小范围修改 Planner、普通 Reviewer 和 fallback Reviewer 的提示词与必要的输入说明，不增加模型阶段。
3. 排查工具失败，并改造 Deep Review 的终结请求，使兼容模型保留原消息前缀；对不兼容模型提供明确、有界的路径。

本规格覆盖旧 Spec 25.5 中可能被理解为“风格、命名和文档问题一律丢弃”的判断规则。其余 Candidate schema、Plan repair、固定 head 工具边界、Cross 契约和 8/12/16 turns 配置保持原样。尤其**不得**在本包把 OCR 的 100 次请求上限搬进 CodeSage。

## 1. 阶段 1：离线质量基线

### 1.1 输入与输出

使用固定三例：`linera-io__linera-protocol@024925d`、`mpv-player__mpv@dbd327d`、`ollama__ollama@b6002f6`。读取 `aacr-bench-main/evaluation/data/aacr_bench.jsonl` 的参考评论、已有 Review 报告、Planner 原始 Draft、repair 后 Plan、Candidate、Reviewer session 与工具调用记录。所有比对在离线脚本或人工审阅中进行；参考评论**不能**进入 Semantic、Planner、Reviewer 的模型输入。

产出一份可复核的基线说明和逐条对照表。每条参考评论至少记录：case、路径/行、主张、`valid_actionable / style_or_docs / factually_incorrect / disputed` 四类之一、分类依据、Plan 是否明确或间接覆盖、Reviewer 是否调查、Candidate 是否同根因命中、是否仍需人工复核。`disputed` 不应强行算作模型的漏报或命中。分类不依据“模型是否输出”反推。

同时分别报告：

- **原始参考 Recall**：沿用数据集原口径，便于与已有实验比较；不得称为“真实缺陷 Recall”。
- **有效问题 Recall**：只以经源码核验、确属本次变更且值得作者处理的参考问题作分母。
- **Candidate 质量**：统计同根因重复、未经证实的假设和“结论为无问题却进入 findings”的项目；不把 Candidate 数量当成效果。
- **执行干扰**：按 session 记录主循环触顶、追加终结、失败工具、超时、缺失的调查步骤，以及可得的 token/cache 数据。不可得的成本或缓存计数保留 `None`，不推算为零。

匹配须比较触发条件、失效机制与修复对象；标题相似或同文件同一行不自动算命中。文件级或跨文件问题可以无精确 hunk，但必须说明证据位置。已知的边界样例要在核验表中显式处理：Linera 的 `'vote_wait` 实际被 `break 'vote_wait` 使用；mpv 的 `mp_rand_seed(0)` 并非“固定为零种子”，且 `mp_rand_state` 声明不是 typedef。其他可疑参考评论仍须逐项核验，不因这几个例子而预判整份数据集。

### 1.2 红线与验收

- 不修改 AACR 数据集、已有报告或 sessions 数据库；不把评价标签写回业务结果。
- 不以三例的百分比推断总体效果，也不把风格/文档意见自动判为无价值。
- 基线表能从给定 commit、参考评论、报告和 session 定位每项结论；对不确定项标注依据不足。
- 本阶段无需真实模型调用，不增加 judge 调用。

## 2. 阶段 2：Plan 与 Reviewer 提示词

### 2.1 Planner：一个调用中的三个检查视角

保留现有一次 `.harness()` 和 `ReviewPlanDraft`。借鉴 PR-AF 的行为/语义、语言与接口契约、系统性跨边界三个视角，但把它们写成**同一 Planner 的选择性思考框架**；不是三个并行 Meta Planner，也不要求每个视角都生成维度。优先识别改变了什么、哪里有独立且内聚的调查问题、哪些文件必须合起来判断。

`review_prompt` 是交给 Reviewer 的工作问题，不是缺陷预测。应说明目标行为或不变量、需要比较的旧/新契约、关键调用方或反例边界、何时可以结束调查。不要把未证实场景写成事实，不要列出过长的逐行操作脚本，不要把某个假说的预期答案塞给 Reviewer。Planner 可以给具体代码锚点，但锚点只是导航；Reviewer 必须自行验证。每个 target 仍须覆盖，部分重叠与包含合并仍按 Spec 25.5A；本包不改 repair 算法。`max_planner_dimensions` 与 `max_final_dimensions` 继续由配置及业务校验负责。

输入材料的信任等级要维持：固定 base/head 和实际 diff 为事实材料；SemanticBrief、Anatomy、PR 描述和 Planner 自己的假设均是线索。Prompt 不得引用 Ground Truth 或要求预先找出 N 个问题。不要靠增加 Planner turns 解决任务书冗长。

### 2.2 Reviewer：独立核验与可行动评论

普通与 fallback Reviewer 使用一致的判断政策：每个 target diff 都要得到判断；Plan 问题是优先线索而非答案。调查以旧/新行为、真实调用路径、守卫条件、下游后果为主。对于接口/类型问题，确认真实生产者和消费者；对于性能问题，说明会重复的操作与触发规模；对于文本/风格问题，说明它为何值得当前 PR 作者修正。

**不再显式排除所有风格、命名、拼写和文档评论。** 这类问题若是本次变更引入或暴露、可在固定 head 核验、可定位、具体可修改，且对可读性、项目约定、用户可见文本或契约说明有实际影响，可以作为低严重度 Finding。仅仅“我更喜欢另一种写法”、与本次变更无关的旧问题、未经证实的项目惯例，仍不应报告。现有 `critical/high/medium/low` 枚举足以承载，不新增 `nitpick` 或 PR-AF 严重度体系，也不要求严重度出现某种分布。

每条 Finding 应给出可核验的主张、为何由这次变更产生、影响和证据；不必对拼写类评论捏造运行时故障路径。对可疑问题先查最强的无害解释或现有 guard。若调查结论是“签名匹配”“此处无越界”“变化是预期行为”，只能写进维度 summary，**不能**为凑覆盖创建 Finding。零 Finding 合法，但 summary 要指出已完成的关键检查和未解决的实际限制。保留单次 Reviewer 内置 worthiness；不增加独立 Post-worthiness Harness。

Prompt 仍分别保存在现有 `planner.md`、`planner_user.md`、`reviewer.md`、`reviewer_fallback.md`、`reviewer_user.md`。修改前先对照三个真实输入的渲染结果，确认动态字段说明不把 Semantic 或 Plan 描述提升为事实。不在 Prompt 中暴露字符截断阈值，不向模型灌输整份严重度/缺陷类型百科，也不改变 Reviewer 输出 Schema。

### 2.3 验收

- 静态 Prompt 测试确认一个 Planner 调用、没有 Ground Truth、没有预设 Finding 数；三个视角仅为选择性检查，不强制三类维度。
- 对已保存的 Planner Draft 与 repaired Plan 做离线回放：调查问题和 cross-reference hints 不因 Prompt 改造而丢失；输入渲染对每种材料的可信度说明明确。
- fake Reviewer 验证：明确证实无问题的结果只有 summary；真实拼写/命名/文档变更可作为 `low` Finding，经现有 mapper 保留；无根据的个人偏好不能因新政策变成自动 Finding。
- 三例真实效果对照必须沿用阶段 1 的双 Recall 与 Candidate 质量口径；模型实验单独 opt-in，保留调用上限和原始报告，不覆盖旧运行。

## 3. 阶段 3A：工具失败与调查可见性

先定位现有 session 中 `invalid_path`、`git_failed`、`tool timeout` 的具体请求及原因，区分模型传错参数、过滤范围外路径、实现故障和仓库规模导致的超时。检查 `file_read`、`file_read_diff`、`code_search` 的路径语义与固定 head 读取；避免 Reviewer 被提示读取工具不接受的路径。必要时只修有证据的工具缺陷或优化查询范围，不全局放宽目录过滤，也不默认提高所有超时时间。

每个 Reviewer 的诊断至少能回答：哪些工具调用失败、是否因此未完成必需调查、最后是自然完成还是触顶终结。不要把“工具失败后模型仍提交了合法 JSON”误标为调查充分。工具输出不得泄露密钥；日志记录错误类别和安全的范围信息，不新增完整 provider 请求体。

验收包括三例失败请求的只读复现或受控夹具；工具修复必须有无需真实模型、无需网络的回归测试。工具无效输入应返回可执行的纠错信息，而不是模糊的空结果。

## 4. 阶段 3B：终结能力与缓存前缀兼容

### 4.1 能力而不是供应商名称

当前 Runtime 根据 provider 元数据决定强制 `FinalizeReview`，并对 DeepSeek 终结请求关闭 thinking；隔离终结还替换 system prompt、删除历史 `tool_use`、改写 `tool_result`、缩小工具集合。这些变化可能使 provider 无法复用调查阶段的 KV Cache，且会改变模型最后看到的证据顺序。不得把“GLM-5.3-flash 一定支持思考中强制工具选择”写成事实，也不得仅以 `provider=...` 推断模型能力。

终结能力至少区分：`thinking_and_forced_tool`、`forced_tool_only_with_thinking_disabled`、`no_forced_tool` 与 `unknown`。能力由明确的模型/端点配置和已验证的 provider 元数据决定；配置能覆盖过时的元数据。日志只记录选定策略与能力来源，不记录密钥。未知能力不能静默降级成错误的 `tool_choice`。

### 4.2 优先保留前缀的终结路径

对支持当前模式下强制工具选择的模型，终结请求保留原 system、原始有序 transcript、已有工具定义及其顺序，只在末尾追加一个清楚要求提交完整 `FinalizeReview` 的用户消息，并在请求层强制该工具。不得为了终结删除/改写旧工具调用或把证据重排成新的消息。强制目标不在活动 Schema 时本地失败关闭；最终结果仍须通过现有 Draft/业务校验。

如果模型只在关闭 thinking 后支持强制工具选择，尽可能仍保留相同消息与工具前缀，**只在该次终结请求**调整 thinking 参数。该参数可能影响服务端缓存，不能承诺缓存必然命中。不能因为一个模型不支持 thinking+forced，就直接走当前的全量 transcript 改写策略。

不支持强制工具选择的模型可用原前缀追加终结提醒、非强制暴露 `FinalizeReview` 的有界路径；若它仍不提交合法结果，再按明确的兼容策略选择隔离兜底或报告 incomplete。旧隔离路径只能是有记录的兼容兜底，不得作为兼容模型的默认路径。不得在 HTTP 400、明确不支持的参数或本地请求预算耗尽后盲目重试；只有**发送前**已确认的能力差异才能选择另一种请求形态。每次策略切换都要有明确原因和严格请求上限。

所有路径保持既有 cancel、deadline、ownership、Schema 校验及“失败不伪装完成”的语义。主循环 turns 上限、终结请求预算和 Schema 纠错次数分别记录，不把终结请求算作“已深入审查”的证据。原 JSON fallback 仍只允许既有恢复用途，不成为默认成功路径。

### 4.3 测试矩阵与观测

使用 fake model client 测试至少四种能力：思考中可强制、须关闭思考才可强制、不可强制、能力未知。对前两种断言发送前的 system、transcript、工具定义顺序与调查末尾完全一致，只追加终结消息；断言仅有 `FinalizeReview` 被接纳。对其他策略断言有界停止、失败归因和不会无限重试。补充 provider 拒绝 `tool_choice`、目标工具缺失、Schema 拒绝首稿、同一工具被重复提交、session 持久化失败等案例。

观察字段至少包含终结策略、能力来源、是否覆盖 thinking、主循环 turns、终结请求数、校验纠错数、终态，以及可得的 `cache_read_tokens`。缓存字段缺失时记 `None`，不能把“消息前缀未改写”写成“已证明缓存命中”。真实 GLM-5.3-flash 的能力与缓存行为须在将来配置该模型后单独做有界验证；本规格不声称已测通。

## 5. 预计代码影响边界与实施交付

| 区域 | 预计修改，不预先规定函数实现 |
|---|---|
| `backend/app/domains/deep_review/prompts/` | Planner 与普通/fallback Reviewer 的任务书及动态字段说明。 |
| `backend/app/domains/deep_review/services/output_formatter.py` | 仅在渲染字段确实缺少必要的可信度/停止条件说明时调整；不重新塞入完整 diff 或历史 transcript。 |
| `backend/app/domains/deep_review/tools/` | 仅修阶段 3A 已复现的路径、搜索或超时问题。 |
| `backend/app/execution_plane/runtime/bridge.py` 及相关 Runtime 边界 | 能力选择、前缀保留终结、受限兼容兜底与诊断；旧 Quick Review 的工具提醒和终结行为不能被意外改变。 |
| `backend/tests/deep_review/`、`backend/tests/execution_plane/` | Prompt、工具、Fake Provider 兼容矩阵、回归与静态边界测试。 |
| `docs/analysis/` 或同级可审计报告 | 三例参考评论对照、Prompt/Plan/Reviewer 归因与实验记录；不写入 `.env` 或 API Key。 |

不改数据库结构、Finding 严重度枚举、Plan repair 算法、Cross 角色数量、Worker/Quick Review 调度，也不引入新 Harness 角色或阶段 4 的动态 turn 策略。实现交付时应分别给出阶段 1 离线基线、阶段 2 提示词对照、阶段 3 工具/终结测试结果与模型兼容矩阵。普通 CI 只跑离线测试；真实模型与缓存效果验证需显式 opt-in 并记录成本边界。
