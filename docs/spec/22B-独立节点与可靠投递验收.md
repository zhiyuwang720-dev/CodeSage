# Spec22B：独立控制面、PR 节点与可靠投递

版本 1.0，2026-09-15。状态：not_started；依赖 22A verified。顺序：**21A → 22A → 22B → 21B → 22C**。

配套：[22A](22A-模块归属与结果事务边界.md)、[22C](22C-远程节点协议与结果投影.md)、[验收台账](22-验收矩阵与实施进度.md)。以下新增配置和接口是目标，不表示当前代码已有。

## 1. 范围与部署契约

一台本地机器：一个 API、两个独立 PR ARQ 节点、PostgreSQL 16、Redis 7、受管共享产物根。使用独立验收库、队列和目录；不买服务器/S3。节点仍是整个 PR 的 owner，三个视角在节点内并行；21B 分包不在本阶段实现。

当前源码默认 worker，队列明确拒绝 inline，保持这一事实；不恢复 Starlette BackgroundTasks 执行。控制面 API 不实例化 LLM/Harness，不因接收任务而启动本地审查 coroutine。

## 2. 22B-R01：独立入口和节点身份

生产入口由 bootstrap 显式提供 control API 与 PR node，旧 worker CLI 可薄包装转发。节点启动加载受信 allowlist：agent_type=pr_review、entrypoint=quick_review、agent_version、协议版本、允许能力和并发值。

节点 node_id 是配置中稳定逻辑 ID；每次进程启动有新 instance_id，记录 PID、hostname、启动时间。attempt 绑定 instance_id，避免同 node_id 的旧进程冒充新进程续租。现有 worker_id 可编码/映射 instance_id，但证据同时保留两者。

节点健康每 5 秒更新、20 秒过期，使用 DB 时间；健康检查用于展示/选择，**不决定执行所有权**。lease 每 5 秒续租、20 秒过期沿现机制；健康在线但 lease 过期仍不可提交。节点退出只注销自身实例。

本阶段允许节点通过受管 repository/UoW 访问同一数据库；这不是凭据隔离。产物路径必须能被两个节点解析，同机共享根为验收前提。远程无共享盘要求见22C。

## 3. 22B-R02：持久化投递和重试职责

采用22A RunCommand。区分三个 ID：task_id 稳定任务；delivery_id 一次提交/resume 的逻辑执行意图；dispatch_id 一次队列投递尝试。resume 生成新 delivery；自动补投只换 dispatch，不重建审查身份。

以 Alembic 增加或复用等价的持久化投递表：task_id、delivery_id（唯一）、command_json/hash、state（pending/dispatched/claimed/closed）、dispatch_generation、next_dispatch_at、last_dispatch_at、dispatch_error、created_at/updated_at。每次物理投递有 dispatch_id 与状态记录或等价审计事件。DB 是事实来源，不能只依赖 Redis job 结果。

业务提交/恢复状态转换与 pending delivery 在同事务完成。发送器短事务领取待投递记录（多实例行锁），网络入队不持业务锁；发送结果写回可重试。ARQ job ID 必须含 delivery+dispatch generation，避免旧结果保留期阻止恢复。消息最大 32KiB，禁止包含完整 diff、prompt、源码和凭据。

为避免“队列入队成功但DB写回失败”造成丢失，发送器在不确定状态可重复投递；owner fencing 必须消除重复有效执行。claim 必须验证 delivery 是任务当前 delivery，旧 delivery 到达不得把当前 delivery 改回去。

**任务级重新投递唯一决策者为 Scale & Ops reconciler**：每5秒扫描 pending/未领取/过期lease运行，持锁确认无有效owner、非终态、未取消、未超过deadline/attempt上限，增加dispatch generation并补投。其行为是系统自动恢复，不是验收脚本手动第二次提交。

ARQ 处理队列/连接执行机制；同一业务失败不再由 ARQ 和节点各自无界重试。有效 owner 冲突不增加业务 attempt，消息返回 deferred/duplicate；下一次有效接管由 reconciler 决定。模型请求级重试保持现 LiteLLM。最终实现需列出 ARQ Retry 分支的保留/移除理由和锁定依赖版本的实测行为。

默认真正领取 attempt 上限3（初次+两次自动恢复），新手动 resume 开始新一轮投递意图但保留历史消耗；deadline 不因自动恢复延长。可恢复环境错误由手动resume，不无限自动拉仓库。超限持锁落可解释的 FAILED；仍有有效owner时不得强行覆盖。

本节 reconciler 是保证长 job_timeout 下90秒接管的最小必要机制：保留正常长任务 timeout（当前3600秒），不能单纯改成几十秒导致长审查被杀。配置名可沿现有设置，但必须在报告给出有效值与机制。worker死后90秒内**新owner claim并开始预检/恢复**，不是要求整个审查90秒完成。

## 4. 22B-R03：背压和资源上限

本地建议默认全局有效运行上限2、每节点1、等待意图上限100；均为可配置值，不是企业容量承诺。已有生产配置不静默覆盖，在示例/验收环境设置。

全局准入采用持久化并发槽或带锁容量行，不用内存计数/无锁count。claim 同事务确认并占槽，slot绑定task/attempt/epoch；续租延长绑定lease，过期按DB时间释放；旧owner释放不得释放新owner槽位。

队列积压按当前未完成的逻辑 delivery 计数，重复dispatch不加等待任务数。管理员取消/查询/resume兼容性检查不被审查准入队列饿死。新提交达到等待上限返回429、稳定overloaded错误码及Retry-After；同一幂等提交返回原任务，不重复占名额。

等待入队任务过deadline不再启动模型，落deadline_exceeded。全局容量变小不强杀已运行任务，暂停新领取直到有效数低于上限。指标同时显示配置容量、有效owner数、排队数。

## 5. 22B-R04：取消、完成、恢复和幂等

取消先持久化cancel_requested并关闭未来投递资格，再通知本地执行/watcher。有效owner可提交受控cancelled；owner已死时reconciler在锁定确认无有效lease后终结取消，不新派发模型。10秒内停止新增测试模型请求，不承诺已发出的外部请求服务端零费用。

resume由PR commands验证输入/配置/产物，再经平台 prepare_resume 事务清取消、新delivery、任务可执行。存在有效owner时拒绝；过期RUNNING不能永久拒绝。已完成任务不再次调用模型，重复请求返回已有结果或明确冲突。

DB commit响应不确定时查询已提交状态/幂等键；不直接重跑模型。完成阶段复用与中断阶段session续跑仍依赖22A结果服务。失效owner的stage、Findings、终态以及以后21B预算写入全部被拒绝。

## 6. 22B-R05：SSE、观测与离线证据

控制面提供持久化运行事件查询，事件有task范围单调序号/稳定ID；SSE Last-Event-ID 可重连到任意API实例。传输至少一次，客户端按event_id去重；历史超出保留窗口时明确gap并返回当前快照，不假装无遗漏。

submit/queue/dispatch/claim/reconcile/cancel/resume/commit 是平台span；preflight/review/turn/model/tool是节点span。跨队列传播trace context，自动恢复新attempt有link和稳定task/run关联。未claim的消息不计有效执行attempt。

按逻辑delivery/attempt分别记录排队时间，端到端时间从首次提交到可见终态，自动恢复不重置起点。模型token/cost由物理provider请求事实累计一次；未知usage/cost显示unknown，不等于0。

失败类型区分 overloaded、delivery_transport_error、owner_conflict、lease_lost、cancelled、preflight_failed、model_error、result_commit_error、attempt_limit_exceeded。高基数task/run/session ID用于trace/log而非Metrics标签。

JSONL和静态HTML可离线浏览，包含身份、请求计数、阶段复用、接管时延、指标和错误。观测导出失败可以降级，但业务checkpoint失败不可吞。

## 7. 22B-R06：验收程序

由统一台账runner启动真实依赖与进程；测试模型使用当前正常模型注入入口、本地HTTP/SSE响应fixture、真实工具、QueryLoop、SessionStore。至少一次只读工具被实际执行。不得mock queue/DB/dispatcher来直接生成completed。

必须覆盖22B-T01—T14。完整、取消恢复、强杀恢复各连续三次；用DB屏障与模型请求记录控制时机。额外测试发送前崩溃、入队成功后写回前崩溃、两个reconciler竞争、旧delivery晚到、重启API/SSE重连。

强杀恢复场景只提交一次用户命令；允许R02系统reconciler自动补投并提供完整审计证据，禁止测试端绕过reconciler enqueue第二条。报告标明“单用户提交+自动补投”，不谎称Redis中始终只有一条物理消息。

完成签收后交接21B：提供owner/UoW端口、节点目录、稳定契约、基线证据；21B只能扩展PR节点业务表与策略，不再修改平台来识别packet/perspective。
