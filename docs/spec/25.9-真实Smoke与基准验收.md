# Spec 25.9：真实 Smoke 与基准验收

版本：1.0。状态：待执行。依赖：25.8 CLI 和 adapter 离线验收通过。
关联：[Plan25](../plan/25-CodeSageDeep-V1核心移植与原型闭环.md) 14.8、Package 25.9；[总索引](25-CodeSageDeep-V1核心移植与原型闭环.md)。

## 1. 本包的目标与结论边界

用一个固定真实 case 验证审查链路、结构化终结、数据库 transcript、领域 JSONL 和 AACR 结果读取是否一起工作。随后对同 case 已有 OCR 结果做可比分析，记录命中、误报候选、token 和耗时。

一个 case 不能证明整体 Recall/Precision 更好。报告必须区分“流程可运行”“该样本表现”“完整 benchmark 结论”。不因为发现了一个缺陷就宣称方案全面优于 OCR，也不能把 partial 运行标为完整验收成功。

## 2. 本包允许修改的文件

主要产出是 docs 下的验收报告和使用说明，原始运行结果保存在 ignored 的独立 run 目录。仅在真实验证发现阻塞缺陷时，修复对应 deep_review 模块并补回归，再单独提交。

不得在验收中重写总体算法、增加 Reviewer 轮次、调整数据集答案、降低 judge 标准或覆盖 OCR 历史输出。共享 Runtime 的缺陷单独记录和提交，不能混入 benchmark 报告伪装为正常执行。

## 3. 执行前必须填写的运行记录

先建立一份具体运行清单。清单未完成前，不启动付费调用。

| 项目 | 必须记录 |
|---|---|
| 代码版本 | CodeSage commit；dirty 状态与改动摘要；Plan/Spec 版本 |
| case | 唯一 instance_id、repo、完整 base/head、实际 merge_base |
| 可信来源 | 数据集名称与本地文件；样本未被临时修改 |
| 模型 | Semantic/Planner/Reviewer/Cross 各角色的模型名和供应商 |
| 限制 | max_duration_seconds、各 max_turns、max_concurrent_reviewers、dimension 上限 |
| 执行授权 | 显式模型调用开关；只运行一个 case |
| 输出位置 | 独立运行目录，保证不覆盖已有 run |
| 数据库 | 现有 Runtime SQL 配置可连接，表已就绪；不记录密码 |
| 对照结果 | 同 case OCR 文件路径及其版本/模型/配置是否可知 |
| judge | 本次是否执行；默认不自动执行 |

模型 key 从 ignored 环境文件或运行环境读取。检查时只报告“已配置/缺失”，不要打印值。也不要将完整 env 保存为复现实验附件。

本 Plan25 以 turn、并发、时长约束为主，没有实现 30K token 硬预算。不要把旧计划的 30K 限制当成本链路已支持能力；若实际需要固定 token 硬上限，应先单独实现验证，不能仅在文档写一个数字。

## 4. 先执行不付费预检

1. 跑 deep_review 和 Runtime 结构化终结回归，记录命令和结果。
2. 使用同一 repo/base/head 跑 --through anatomy，检查 review_paths、context_paths、过滤原因和 merge_base。
3. 确认目标 case 的源码和 diff 可读取，工具固定 head，不依赖 dirty 工作区。
4. 验证数据库配置和模型路由可解析，禁止在预检中隐式发模型请求或自动运行迁移。
5. 检查输出目录可写、足够独立；记录本次 case 数为 1，外层没有批量并发。
6. 检查 CLI --help 包含实际参数。以下命令只能在 25.8 已实现对应开关后使用。

固定本地源码 smoke 示例（不能替代真实 AACR case）：

```powershell
Set-Location E:/Mac/CodeSage/backend
python -m app.domains.deep_review --repo E:/Mac/CodeSage --base a4595a82 --head a9b0f49e --through anatomy --output .codesage/deep-review/preflight.json
```

AACR 验收必须使用选定 ReviewInstance 的 repo/base/head，不把上述两个 CodeSage commit 伪装成 AACR 样本。

## 5. 真实审查执行步骤

1. 固定运行清单，不在执行途中换模型或扩大文件集合。
2. 通过 25.8 adapter 或独立 CLI 启动一个 case；真实 CLI 显式传 --through final --allow-model-calls。
3. 日志观察阶段是否前进。收到 timeout、provider 错误或 schema 无法终结时保留原始诊断，不手工补造成功 JSON。
4. 运行结束后先检查退出码，再检查 status、deferred/failed 维度、Cross fallback 和 usage_complete。
5. 检查 result.json、events.jsonl、adapter envelope 是否对应同一 run/case/commit。
6. 用现有 AACR 读取器离线读取 comments，确认非空 Findings 没有被映射成空列表。
7. 停止本次付费执行，先分析结果。不要自动继续全数据集，也不自动重跑失败 case。

直接 CLI 模板（占位值替换为运行清单中的真实值）：

```powershell
python -m app.domains.deep_review --repo <local-repo> --base <base-sha> --head <head-sha> --through final --allow-model-calls --output <new-run-dir>/review.json --store-dir <new-run-dir>/domain
```

失败后修复代码需要创建新 run。报告同时保留失败与成功运行，不能删除第一次费用和耗时来美化指标。

## 6. 运行结果核验

逐项核对：

- 每个允许 review 文件有活动 owner，或明确 deferred；覆盖缺口可解释。
- 每个非 deferred Reviewer 有成功或失败记录；成功零 Finding 也是有效结果。
- Findings 的 source、dimension、路径和行号合法，正文能追溯到本次变更。
- Cross 对所有 Candidate 有裁决，或明确采用 keep-all fallback。
- 最终 drop/new/dedup/filter 数量可以与输入 Candidate 数量核对。
- 日志记录各 Agent session_id；现有 SQL transcript 能按该 session 查询。禁止把领域 JSONL 当成完整模型 transcript。
- 总墙钟与各阶段耗时有记录。并行阶段耗时不简单相加。
- usage 不完整则报告未知或已知下界；成本缺失则 None，不能写 0。
- 原始输出不含密钥、完整环境变量或 secret 文件内容。

若数据库 transcript 无法访问，标记诊断验证未完成，不声称 SQL 闭环已验收。Phoenix 不是本包新增强制验收范围；已有 Trace 可作为附加证据，缺失不能诱导实施者另建观测平台。

## 7. 效果评测与 OCR 对照方法

先做人工问题级对照或现有离线答案匹配。需要运行 judge 时，必须显式选择 eval 阶段并单独记录模型、费用和耗时；review 成功不会自动授权一轮或多轮 judge。

同 case 对照表至少包含：

| 指标 | CodeSageDeep | OCR | 口径要求 |
|---|---|---|---|
| 原始/最终 Finding 数 | 分开记录 | 已有结果数量 | 不把数量当质量 |
| 命中 | 问题级匹配 | 同方法匹配 | 不按相似文字猜命中 |
| 误报候选 | 人工或 judge 待确认项 | 同口径 | 未确认不能当 FP 定论 |
| 漏报 | 已知答案中未命中项 | 同口径 | 标明答案覆盖限制 |
| 总墙钟 | 秒 | 秒 | 区分是否包含仓库准备 |
| token | 实测或未知 | 实测或未知 | 同供应商统计口径才直接比较 |
| cost | 实测或 None | 实测或 None | 不伪造美元估计 |
| 模型阶段/请求数 | 分开说明 | 按已有记录 | Harness 数不能与请求数混用 |
| 运行完整性 | completed/partial/failed | 已知状态 | partial 需解释影响 |

若 OCR 的模型/版本/配置不可知，写成历史观察对照，不给严格胜负结论。一个样本的命中/漏报分析只用于决定下一步实验，不能宣称总体统计显著性。

## 8. 测试与验收场景

| 编号 | 场景 | 应得到的交付证据 |
|---|---|---|
| S01 | 无真实 key/数据库缺失 | 清晰阻塞说明，零付费请求，不伪造通过 |
| S02 | 一个正常真实 case | 完整结果、事件、session 关联与 adapter 读取 |
| S03 | provider/schema 失败 | 新 run 的失败记录，费用未知项明确 |
| S04 | partial | 保留有效发现，说明覆盖/验证缺口 |
| S05 | judge 未运行 | 报告标注未评测，不伪造命中指标 |
| S06 | 同 case 历史 OCR 数据缺字段 | 对照表写未知，说明可比性限制 |
| S07 | 敏感信息检查 | 提交附件不包含密钥原文 |
| S08 | 修复后重新执行 | 新 run_id；第一次结果未被覆盖 |

S03/S04 的真实付费故障不需要故意制造。其失败机制已由前包离线注入测试覆盖；本包记录实际出现的情况即可。

## 9. 交付文件与完成标准

新增 docs 下的 25.9 验收报告，至少包含运行清单、精确执行命令（密钥除外）、代码版本、测试结果、结果路径、状态、数量核对、用量/耗时表、OCR 对照、失败记录和结论限制。

完成分成两部分明确报告：

1. 工程验收通过：真实 final 链路 completed，文件与 SQL 关联可核验，AACR 可读取结果。
2. 效果分析完成：同 case 对照有证据支持；若缺 judge/答案/OCR 元数据，列出未完成项，不把工程通过等同于效果胜出。

partial 可以形成有价值的诊断报告，但不能把完整流程验收勾为通过。没有真实运行条件时保留待执行状态，交付预检与阻塞原因。

建议提交只包含验收说明、必要脱敏小样和经测试的独立 bugfix。大体积原始输出保留在 ignored 目录，通过路径和 hash 引用。
