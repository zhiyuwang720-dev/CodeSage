## 2. ① 输入层 CLI

### 数据流

```
终端输入
  ├─ REPL 模式: _read_line(Windows msvcrt 捕获 Ctrl+O=0x0F)
  │     ├─ 斜杠命令 → /commands 注册表(help/mode/clear/exit…)
  │     └─ 普通输入 → run_single_turn(挂 on_stream + on_tool_event)
  ├─ 单次模式: CLI 参数直接进一次 run,ask 决策默认拒绝(安全默认)
  ├─ --continue: 读最近会话 JSONL → history 注入主循环(自然续接)
  └─ 运行中插话: 捕获线程(GIL 原子 append)→ steer_queue
        · 门控:capture_gate 只在 run_single_turn 期间置位,不与主提示竞争
        · 单一事实来源:引擎已消费的消失,剩余成为下一轮输入
```

### 设计要点

- **双模式共用 run_single_turn**:REPL 与测试/CI 同一入口,`--output-format json` 输出 RunSummary 机器可读结果。
- **steer_queue 单一事实来源**:捕获线程只做 `captured_lines` 追加(线程安全),主线程在每轮前后转移入 asyncio 队列;`_transfer_captured` / `_drain_steer_queue` 分工,引擎消费过的不会重复执行。
- **Ctrl+O 转录模式**:msvcrt 裸读捕获 0x0F,`transcript=True` 时渲染层显示完整工具输出与 thinking(见 ⑫)。
- **优雅退出**(CC-11):首信号 set abort(工具协作式中断),二信号强制 exit(130);清理预算 5s,超时 `os._exit` failsafe。

## 3. ② 主循环(引擎心脏)

### 局部流程(完整状态机)

```
                    ┌────────────────────────────┐
        ┌──────────→│ 检查点1:turn≥max_turns?     │──是→ stop("max_turns")
        │           │ max_budget 超?             │──是→ stop("max_budget")
        │           │ abort?                     │──是→ stop("interrupted")
        │           └────────────┬───────────────┘
        │                        ▼
        │           drain steer_queue → user_message 逐条入列表
        │                        ▼
        │           _ask_model(messages) ──中断──→ stop("interrupted")
        │                        ▼
        │           yield assistant; 持久化; 入列表
        │                        ▼
        │           有 tool_use? ──无──→ thinking-only?──是→ 注入恢复消息(≤3次)
        │              │有                    │否             │是超限
        │              ▼                      ▼               ▼
        │           检查点2:abort?     last_stop_reason="completed"→ return
        │              │否                  stop("thinking_only_exhausted")
        │              ▼
        │           ToolUseQueue.run()(⑤权限内嵌,⑥调度)
        │              ▼
        │           tool_result 逐工具 yield + 持久化 + 入列表
        │              ▼
        │           全批 terminate?(⑩)──是→ stop("tool_terminated")
        │              │否
        └──────────────┘(回到检查点1,消息列表持续增长)
```

### 设计要点

- **显式 while 迭代,非递归**(R1 解法):Kode 的 `messagePipelineCore` 递归 `yield*` 自身,Python 在 ~1000 轮(recursionlimit)必然 RecursionError。while + 可增长消息列表:同一透明消息流、零栈增长 —— **2001 轮压力测试通过**(设计为超过默认限制 2 倍)。
- **三检查点中断**:循环顶部、LLM 调用后、工具批前;abort 是 `asyncio.Event`,产物是 `is_meta` 消息(`(interrupted by user)`),normalize 时过滤,不进模型上下文。
- **错误自愈**:工具抛异常/权限拒绝/未知工具/非法输入 → 全部转 `is_error` 的 tool_result 消息,模型看见失败自己调整 —— 循环永不因工具失败崩溃;唯一硬性停止是有界预算。
- **每轮全量 normalize**:消息列表是唯一上下文,阶段 10 压缩解决 O(n²)(见 `docs/modules/06-engine.md`)。

## 4. ③ 消息契约(全系统唯一消息形状)

### 数据流

```
adapter 流式事件 ─→ collect 拼装 ─→ LLMResponse ─→ assistant_message()
                                                     │
          工具结果 ─→ ContentBlock(tool_result) ─→ user_message()
                                                     │
                        所有消息 → SessionMessage(role/content/usage/is_meta/
                                                 is_error/error_message)
                                                     │
        normalize_for_api(过滤 is_meta、合并相邻 user) ─→ LLMRequest
```

### 设计要点

- **Anthropic 式 ContentBlock 是全系统唯一消息形状**(主规格不变量 #1):`text / thinking / tool_use / tool_result` 四种块;OpenAI/DeepSeek 差异只在 adapter 边界转换(usage 归一化、`reasoning_content` → thinking 块)。
- **SessionMessage 统一封装**:带 `usage`(LLM 调用统计)、`is_meta`(harness 合成消息,进会话但不进模型)、`is_error` / `error_message`(provider 错误详情透传,修复过「provider error 无详情」问题)。
- **工具级消息流契约**:每个工具一条 tool_result 消息(而非整批合并),UI 可边收边渲染,会话顺序稳定。
- **thinking-only 检测**:assistant 只含 thinking 块 → 注入恢复消息重试,3 次有界(⑩)。

## 5. ④ LLM 调用链(ai/client.py)

### 局部流程

```
model="main" (指针)                     
    │ resolve_profile: 指针链 → profile名 → 字面量      
    ▼                                   
adapter 选择 (provider, model) 缓存 
    ▼                                   
with_retry ──→ with_cancel ──→ adapter.astream()     
    │            (cancel_event)          
    ▼                                    
流式事件序列(text_delta / thinking_delta /            
  tool_use_start / tool_use_delta / usage /            
  error / done)                                       
    │ 首事件前失败 → 一次性重试(网络抖动)              
    ▼                                                  
collect 拼装 → LLMResponse ──→ _drop_truncated_tool_uses┘
    │                                                   
    ├─ 非 main 且失败可恢复(401/403/404/429/5xx/网络) → 回退 main profile
    ├─ usage → total_cost += estimate_cost(模型, usage)
    └─ 返回组装后的 response(含错误编码,不 throw)
```

### 设计要点

- **模型指针**(主规格不变量 #6):`main/task/compact/quick` → profile → 字面量(`provider:model`);辅助请求失败自动回退 main(`_is_fallback_eligible` 判定,取消请求绝不静默重试)。
- **重试在 client,不在 adapter**:`with_retry` 尊重 retry-after;`with_cancel` 逐事件检查 cancel_event(流卡在 provider 内部是已接受的简化)。
- **流式 = 事件流,拼装 = collect**:UI 通过 on_stream tee 拿实时 delta,引擎拿拼装结果 —— 同一个流两种消费(见 ⑨)。
- **length 截断保护**(PI-03):`stop_reason=="length"` 或参数带 `$partial_json` 哨兵 → 丢弃残缺 tool_use,模型看到错误消息重新发起 —— 残缺参数绝不进入执行链。
- **成本双路径累计**:非流式在 complete 后、流式从 usage 事件,`total_cost[0]`(list 便于跨 client 共享)。

## 6. ⑤ 权限决策链(permissions/engine.py)

### 局部流程(9 步,deny 绝对)

```
evaluate_tool_use(tool_name, tool_input, mode, cwd, permissions…)
  │ 预计算:合并 settings+session 规则、路径双候选(lexical+real)
  ▼
 1. 系统白名单(SYSTEM_TOOLS)        ──命中→ allow
 2. Bash 命令静态分析(子命令级)      ──deny→ DENY / ask→ ask(需显式批准)
 3. 显式规则 deny>ask>写保护>allow   ──deny→ DENY / ask→ ask
    (Bash 按子命令:任一 denied 子命令否定整条 compound)
 4. 写保护路径(硬地板)               ──命中→ ask(需显式批准,allow 也压不住)
 5. 文件工具:目标必须在工作目录内    ──出树→ ask(需显式批准,yolo 也不放)
 6. 敏感路径(.env/key/凭据)         ──命中→ ask(需显式批准)
 7. needs_permissions() 自声明       ──False→ allow(只读工具)
 8. 模式后处理:plan 拒写 / 显式批准集 / yolo 自动放行 ask(不碰显式批准项)
 9. 默认:ask(未知工具绝不默认放行)
  │
  ▼ 每个决策 → _decide → 恰好一条 ToolAuditEvent(工具/决策/来源/模式/路径摘要)
```

### 设计要点

- **决策顺序固定:deny > ask > allow**,deny 不可被任何模式绕过(yolo 只自动放行「ask」类)。
- **写保护是硬地板**:显式 allow 规则也压不过写保护路径 —— 权限的底线不在规则里,在路径层。
- **路径双候选**:`[词法绝对路径, symlink 展开的真实路径]`,规则匹配任一候选 —— 对 `/tmp/link/**` 的 deny 在 link → `~/.ssh` 时依然成立(路径层防御,不被符号链接绕过)。
- **Bash 特殊处理**:子命令拆分后逐条评估(Bash(<cmd>) 内容规则),`require_all` 语义区分 allow/deny/ask 三态;`=`cmd 注入防护、rm 保护、`cd` 约束见 `bash_rules.py`。
- **每次决策恰好一条审计事件**:路径摘要只含路径不含内容/密钥(审计安全)。
- **工作目录约束绝对化**:出树访问在 yolo 下也需显式批准(Kode `isPathInWorkingDirectories` 语义)。

## 7. ⑥ 工具调度(engine/tool_queue.py)

### 局部流程(三阶段管道,PI-02)

```
ToolUseQueue.run()
  │ 分批:连续 is_concurrency_safe 工具 gather 并行
  │       非安全工具 = 屏障(独占一批,串行)
  ▼
┌─ _execute(item) ──────────────────────────────────────┐
│ prepare : abort? → pre_hook → 权限检查                │
│           denied → metadata.error_code="permission_blocked"│
│                    → post_hook → 返回 denied          │
│ execute : on_tool_event("start")                     │
│           async for partial in tool.call(input, ctx)  │
│             ToolProgress → on_tool_event("update")    │
│           ToolError → ToolResult(err, code=exc.code)  │
│           on_tool_event("end")                       │
│ finalize: 空输出 → "(name completed with no output)"  │
│           _spill_large_result(>100K 落盘)             │
│           finalize 回调(结果改写口) → post_hook       │
└──────────────────────────────────────────────────────┘
  ▼
批内任一失败?
  ├─ 已完成兄弟保留真实结果(CC review:作废成功读结果是净损失)
  └─ 未启动兄弟 + 后续队列 → <tool_use_error>Sibling tool call errored</tool_use_error>
```

### 设计要点

- **并发屏障**:`is_concurrency_safe` fail-closed 默认 False —— 只有显式声明只读的工具才并行,写工具天然串行。
- **sibling 作废语义(软化版)**:一个失败 → 已完成的保留、未启动的作废 —— 「写失败可能已污染环境,投机兄弟不得执行」;模型必须显式处理失败,不假装成功。
- **三阶段管道**:prepare(权限/校验串行,全部检查过才并发)→ execute(结果按源顺序回报)→ finalize(结果改写集中在单点)。
- **生命周期事件**(PI-01):start/update/end 三事件,`on_tool_event` 回调异常隔离(logging,不破坏工具);CLI 消费为 `● name running…` 状态行。
- **spill 幂等**(CC-08):`>100K` 字符落盘,路径按 tool_use_id 确定性生成 —— 重放相同 id 复用文件,prompt-cache 前缀稳定。

## 8. ⑦ 工具契约(tools/base.py)

```
Tool(扁平对象,非类层级)
  name / description / input_schema     ← 元数据,spec() → 模型可见
  is_concurrency_safe = False           ← 并发声明(fail-closed)
  needs_permissions(input) → bool       ← 权限自声明(引擎消费,工具内不自行判断)
  validate_input(input) → raise ToolError ← 执行前校验
  async call(input, ctx) → AsyncIterator[ToolResult]
      ├─ yield ToolProgress(text) 若干   ← 实时 UI,不进模型
      └─ yield ToolResult 一次           ← 最终结果,模型可见
ToolUseContext(cwd, env, abort_event, 读新鲜度状态, read_cache)
ToolResult(content, is_error, terminate, new_messages, metadata)
ToolError(msg, code)                   ← 稳定错误码(PI-12),不解析消息
```

### 设计要点

- **扁平对象 + async generator**;`ToolProgress` 是瞬态进度(只给 UI),`ToolResult` 是终值(给模型)。
- **权限永远在引擎,不在工具内**:`needs_permissions()` 自声明被决策链第 7 步消费;工具作者不为权限负责 —— 与 is_concurrency_safe 自声明同一哲学(契约驱动,引擎保持简单)。
- **terminate 语义**(PI-04):工具可请求「本批后停」,但引擎只在**全批同意**时停止 —— 避免单一工具误判终止(⑩)。
- **ToolUseContext 注入**:引擎构造一次复用于整轮,承载 abort 通道 + Read 新鲜度(`read_file_timestamps/hashes`)+ 去重缓存(read_cache)。

## 9. ⑧ 内置工具族(tools/builtin/)

| 类别 | 工具 | 关键行为 |
|---|---|---|
| 文件系统 | `LS` / `Read` / `Write` / `Edit` | Read 记录 mtime+hash,Edit/Write 覆盖前校验(防外部修改被静默覆盖);同参数重读(未变更)返回 stub(CC-06 去重) |
| 搜索 | `Glob` / `Grep` | rg 双轨(rg 缺失回退纯 Python) |
| Shell | `Bash` | 静态破坏性命令防护、cd jail(agent_call 只能 cd 到 cwd 内)、硬超时+进程树击杀(taskkill /T / killpg)、Windows 优先 Git Bash 执行、`run_in_background` |
| 系统 | `TaskOutput` / `TaskStop` | 后台任务生命周期 |
| 交互 | `TodoWrite` | 系统白名单工具(模型不可见/不参与权限) |
| 网络 | `WebFetch` | SSRF 防护 |

### 设计要点

- **目录规范**(主规格强制):每工具一文件、类别子包、tests 镜像 `tests/tools/builtin/<类别>/test_<file>.py`。
- **Bash 是权限最重的工具**:`REQUIRES_EXPLICIT_APPROVAL`(yolo 也不自动放行)+ 双层静态防护(工具内 check_destructive/check_cd + 引擎内 bash_rules 分析)。
- **Windows 一等公民**:Git Bash 执行 POSIX 语法(`_shell_argv` 探测)、`/e/Mac/...` 路径归一化(Path 会错误挂到当前盘符)、平台提示写入系统提示词。

## 10. ⑨ Hook 与回调

```
                    ┌─────────────────────────────────────────────┐
 loop.on_stream     │ 流式事件 tee:UI 实时 delta,引擎拿拼装结果    │
   (UI 消费)         │ 闭包陷阱:tee 内引用外层 stream → 捕获 inner  │
                    │ 副本(Python 闭包晚绑定修复)                 │
 loop.on_tool_event │ start/update/end 生命周期,异常隔离          │
   (UI 消费)        │ CLI 消费:● name running… 状态行             │
 loop.finalize      │ 结果改写口(PI-02):工具结果落地前可替换       │
   (扩展消费)        │ 例:脱敏、摘要、注入                            │
 request_permission │ ask 决策 → 用户确认回调(REPL 接 UI)         │
   (引擎→UI)        │ 无回调 = 拒绝(安全默认)                      │
 pre_hook/post_hook │ 阶段 09 预留(ToolUseQueue 构造参数已就位)   │
   (未接线)         │                                               │
└─────────────────────────────────────────────────────────────┘
```

### 设计要点

- **消费方解耦**:主循环只发消息与事件,CLI/测试/未来插件各自订阅 —— 与 pi 的订阅者模型同构但更轻。
- **回调失败隔离**:`on_tool_event` 抛异常只记日志,绝不打断工具执行;UI/遥测是 best-effort。
- **单流双消费**:on_stream tee 让「边收边渲染」与「collect 拼装」共存,`inner = stream` 捕获副本避免 RuntimeError(已修的真实 bug)。

## 11. ⑩ 终止与恢复语义

| 原因(last_stop_reason) | 触发 | 产物 |
|---|---|---|
| `completed` | 模型终答(无 tool_use) | 正常结束 |
| `max_turns` / `max_budget` | 检查点 1 | is_meta 说明消息 |
| `interrupted` | abort(三检查点) | `(interrupted by user)` is_meta |
| `tool_terminated` | 批内**全部**工具 terminate(PI-04) | `Stopped: tools requested termination.` |
| `thinking_only_exhausted` | 3 次 thinking-only 恢复重试后 | is_meta 放弃消息 |
| `error` | 不可恢复 LLMError | `(provider error: …)` is_error 消息 |

### 设计要点

- **结构化终止原因**(CC-10):`last_stop_reason` 替代文本嗅探,CLI/测试按原因分支(`--output-format json` 暴露 `max_turns_exceeded` 等)。
- **terminate 全批同意**:逐个工具检查 `result.terminate`,全 True 才停;检查放在结果已 yield 之后 —— 模型/用户仍能看到工具做了什么。
- **thinking-only 有界重试**:恢复消息不计轮次(`turn -= 1`),重试预算与轮次预算是两个独立有界维度。

```
流式文本:  逐完整行打印(未完成的行缓冲)—— CC 行为

```

- 纯文本 ANSI(CYAN/DIM/YELLOW/RED/GREEN),`isatty()` 决定是否着色。
- 渲染与引擎完全解耦:消费 SessionMessage 流 + on_stream/on_tool_event,不感知内部机制。

## 14. 总览:横切设计原则

1. **单一信息通道**:Message 流是唯一通道 —— 工具结果、中断、错误、终止都是消息,消费方对内部机制无感知。
2. **错误自愈**:工具失败转 error tool_result 交模型调整,循环永不崩;唯一硬性停止是有界预算。
3. **安全默认**:ask 无回调 → 拒绝;未知工具默认 ask;并发 fail-closed;deny 不可绕过。
4. **有界性**:max_turns / max_budget / 重试次数 / 结果落盘阈值 / 清理预算全部有界。
5. **可测可注**:依赖全部构造注入,session 可选,queue 可断言 —— 395 项测试全绿。
6. **契约驱动**:并发安全、权限需求都由工具自声明,引擎保持简单、单点决策。
