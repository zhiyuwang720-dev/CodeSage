## 2. ① 输入层 CLI

### 数据流

```
终端输入
  ├─ REPL 模式: _read_line(Windows msvcrt 捕获 Ctrl+O=0x0F)
  │     ├─ 斜杠命令 → /commands 注册表(help/mode/clear/exit…)
  │     └─ 普通输入 → run_single_turn(挂 on_stream + on_tool_event)
  ├─ 单次模式: CLI 参数直接进一次 run,ask 决策默认拒绝(安全默认)
  ├─ --continue: 读最近会话 JSONL → history 注入主循环(自然续接)
  └─ 运行中插话: 捕获线程(GIL 原子 append)→ steer_queue
        · 门控:capture_gate 只在 run_single_turn 期间置位,不与主提示竞争
        · 单一事实来源:引擎已消费的消失,剩余成为下一轮输入
```

### 设计要点

- **双模式共用 run_single_turn**:REPL 与测试/CI 同一入口,`--output-format json` 输出 RunSummary 机器可读结果(10 个 key,含 `budget_exceeded` / `permission_denials`)。
- **steer_queue 单一事实来源**:捕获线程只做 `captured_lines` 追加(线程安全),主线程在每轮前后转移入 asyncio 队列;`_transfer_captured` / `_drain_steer_queue` 分工,引擎消费过的不会重复执行。
- **Ctrl+O 转录模式**:msvcrt 裸读捕获 0x0F,`transcript=True` 时渲染层显示完整工具输出与 thinking(见 ⑫)。
- **优雅退出**(CC-11):首信号 set abort(工具协作式中断),二信号强制 exit(130);清理预算 5s,超时 `os._exit` failsafe;退出经事件循环顶层抛出,不在 task 内 sys.exit(避免 orphan task 异常导致进程退不出)。

## 3. ② 主循环(引擎心脏)

### 局部流程(完整状态机,含 ⑭ 压缩检查点)

```
                    ┌────────────────────────────┐
        ┌──────────→│ 检查点1:turn≥max_turns?     │──是→ stop("max_turns")
        │           │ max_budget 超?             │──是→ stop("max_budget")
        │           │ abort?                     │──是→ stop("interrupted")
        │           └────────────┬───────────────┘
        │                        ▼
        │           drain steer_queue → user_message 逐条入列表
        │                        ▼
        │           ⑭ 压缩检查点:auto 阈值 / PTL 反应式(见第 15 节)
        │                        ▼
        │           _ask_model(messages) ──中断──→ stop("interrupted")
        │           (⑬ context reminder 前置注入)
        │                        ▼
        │           yield assistant; 持久化; 入列表
        │                        ▼
        │           有 tool_use? ──无──→ thinking-only?──是→ 注入恢复消息(≤3次)
        │              │有                    │否             │是超限
        │              ▼                      ▼               ▼
        │           检查点2:abort?     last_stop_reason="completed"→ return
        │              │否                  stop("thinking_only_exhausted")
        │              ▼
        │           ToolUseQueue.run()(⑤权限内嵌,⑥调度,⑨ pre/post_hook)
        │              ▼
        │           tool_result 逐工具 yield + 持久化 + 入列表
        │              ▼
        │           全批 terminate?(⑩)──是→ stop("tool_terminated")
        │              │否
        └──────────────┘(回到检查点1,消息列表持续增长)
```

### 设计要点

- **显式 while 迭代,非递归**(R1 解法):Kode 的 `messagePipelineCore` 递归 `yield*` 自身,Python 在 ~1000 轮(recursionlimit)必然 RecursionError。while + 可增长消息列表:同一透明消息流、零栈增长 —— **2001 轮压力测试通过**(设计为超过默认限制 2 倍)。
- **三检查点中断**:循环顶部、LLM 调用后、工具批前;abort 是 `asyncio.Event`,产物是 `is_meta` 消息(`(interrupted by user)`),normalize 时过滤,不进模型上下文。
- **错误自愈**:工具抛异常/权限拒绝/未知工具/非法输入 → 全部转 `is_error` 的 tool_result 消息,模型看见失败自己调整 —— 循环永不因工具失败崩溃;唯一硬性停止是有界预算。
- **每轮全量 normalize,压缩已落地**:O(n²) 上下文增长由 ⑭ 压缩检查点解决(阈值 111,616 token / PTL 反应式),压缩不计轮次、不是终止条件(见第 15 节)。

## 4. ③ 消息契约(全系统唯一消息形状)

### 数据流

```
adapter 流式事件 ─→ collect 拼装 ─→ LLMResponse ─→ assistant_message()
                                                     │
          工具结果 ─→ ContentBlock(tool_result) ─→ user_message()
                                                     │
                        所有消息 → SessionMessage(role/content/usage/is_meta/
                                                 is_error/error_message)
                                                     │
        normalize_for_api(过滤 is_meta、合并相邻 user、
        is_reminder 抽离前置、is_compaction_summary 保位) ─→ LLMRequest
```

### 设计要点

- **Anthropic 式 ContentBlock 是全系统唯一消息形状**(主规格不变量 #1):`text / thinking / tool_use / tool_result` 四种块;OpenAI/DeepSeek 差异只在 adapter 边界转换(usage 归一化、`reasoning_content` → thinking 块)。⑬⑭ 的产物都是 user 消息 —— 注入不新增消息形状。
- **SessionMessage 统一封装**:带 `usage`(LLM 调用统计)、`is_meta`(harness 合成消息,进会话但不进模型)、`is_error` / `error_message`(provider 错误详情透传,修复过「provider error 无详情」问题)。
- **标记型字段**(V0.2 新增):`is_reminder`(上下文/恢复提示,请求视图抽离**前置合并**,不进会话日志)、`is_compaction_summary`(压缩摘要,**保位不合并**,与相邻 user 消息永不相融)—— 两者语义分离,normalize 各一条规则(core/normalize.py)。
- **工具级消息流契约**:每个工具一条 tool_result 消息(而非整批合并),UI 可边收边渲染,会话顺序稳定。
- **thinking-only 检测**:assistant 只含 thinking 块 → 注入恢复消息重试,3 次有界(⑩)。

## 5. ④ LLM 调用链(ai/client.py)

### 局部流程

```
model="main" (指针)                     
    │ resolve_profile: 指针链 → profile名 → 字面量      
    ▼                                   
adapter 选择 (provider, model) 缓存 
    ▼                                   
with_retry ──→ with_cancel ──→ adapter.astream()     
    │            (cancel_event)          
    ▼                                    
流式事件序列(text_delta / thinking_delta /            
  tool_use_start / tool_use_delta / usage /            
  error / done)                                       
    │ 首事件前失败 → 一次性重试(网络抖动)              
    ▼                                                  
collect 拼装 → LLMResponse ──→ _drop_truncated_tool_uses┘
    │                                                   
    ├─ 非 main 且失败可恢复(401/403/404/429/5xx/网络) → 回退 main profile
    ├─ usage → total_cost += estimate_cost(模型, usage)
    └─ 返回组装后的 response(含错误编码,不 throw)
```

### 设计要点

- **模型指针**(主规格不变量 #6):`main/task/compact/quick` → profile → 字面量(`provider:model`);辅助请求失败自动回退 main(`_is_fallback_eligible` 判定,取消请求绝不静默重试)。⑭ 摘要请求走 `compact` 指针(见第 15 节)。
- **重试在 client,不在 adapter**:`with_retry` 尊重 retry-after;`with_cancel` 逐事件检查 cancel_event(流卡在 provider 内部是已接受的简化)。
- **流式 = 事件流,拼装 = collect**:UI 通过 on_stream tee 拿实时 delta,引擎拿拼装结果 —— 同一个流两种消费(见 ⑨)。
- **length 截断保护**(PI-03):`stop_reason=="length"` 或参数带 `$partial_json` 哨兵 → 丢弃残缺 tool_use,模型看到错误消息重新发起 —— 残缺参数绝不进入执行链。
- **成本双路径累计**:非流式在 complete 后、流式从 usage 事件,`total_cost[0]`(list 便于跨 client 共享)。

## 6. ⑤ 权限决策链(permissions/engine.py)

### 局部流程(9 步,deny 绝对)

```
evaluate_tool_use(tool_name, tool_input, mode, cwd, permissions…)
  │ 预计算:合并 settings+session 规则、路径双候选(lexical+real)
  ▼
 1. 系统白名单(SYSTEM_TOOLS)        ──命中→ allow
 2. Bash 命令静态分析(子命令级)      ──deny→ DENY / ask→ ask(需显式批准)
 3. 显式规则 deny>ask>写保护>allow   ──deny→ DENY / ask→ ask
    (Bash 按子命令:任一 denied 子命令否定整条 compound)
 4. 写保护路径(硬地板)               ──命中→ ask(需显式批准,allow 也压不住)
 5. 文件工具:目标必须在工作目录内    ──出树→ ask(需显式批准,yolo 也不放)
 6. 敏感路径(.env/key/凭据)         ──命中→ ask(需显式批准)
 7. needs_permissions() 自声明       ──False→ allow(只读工具)
 8. 模式后处理:plan 拒写 / 显式批准集 / yolo 自动放行 ask(不碰显式批准项)
 9. 默认:ask(未知工具绝不默认放行)
  │
  ▼ 每个决策 → _decide → 恰好一条 ToolAuditEvent(工具/决策/来源/模式/路径摘要)
```

### 设计要点

- **决策顺序固定:deny > ask > allow**,deny 不可被任何模式绕过(yolo 只自动放行「ask」类)。
- **写保护是硬地板**:显式 allow 规则也压不过写保护路径 —— 权限的底线不在规则里,在路径层。⑨ 的 `hook_allowed` 短路是 allow 侧唯一例外,且写保护地板依然压它(见第 10 节)。
- **路径双候选**:`[词法绝对路径, symlink 展开的真实路径]`,规则匹配任一候选 —— 对 `/tmp/link/**` 的 deny 在 link → `~/.ssh` 时依然成立(路径层防御,不被符号链接绕过)。
- **Bash 特殊处理**:子命令拆分后逐条评估(Bash(<cmd>) 内容规则),`require_all` 语义区分 allow/deny/ask 三态;`=`cmd 注入防护、rm 保护、`cd` 约束见 `bash_rules.py`。
- **每次决策恰好一条审计事件**:路径摘要只含路径不含内容/密钥(审计安全)。
- **工作目录约束绝对化**:出树访问在 yolo 下也需显式批准(Kode `isPathInWorkingDirectories` 语义)。

## 7. ⑥ 工具调度(engine/tool_queue.py)

### 局部流程(三阶段管道,PI-02,⑨ 已接线)

```
ToolUseQueue.run()
  │ 分批:连续 is_concurrency_safe 工具 gather 并行
  │       非安全工具 = 屏障(独占一批,串行)
  ▼
┌─ _execute(item) ──────────────────────────────────────┐
│ prepare : abort? → ⑨ PreToolUse 钩子 → 权限检查        │
│           denied → metadata.error_code="permission_blocked"│
│                    → ⑨ post_hook → 返回 denied        │
│ execute : on_tool_event("start")                     │
│           async for partial in tool.call(input, ctx)  │
│             ToolProgress → on_tool_event("update")    │
│           ToolError → ToolResult(err, code=exc.code)  │
│           on_tool_event("end")                       │
│ finalize: 空输出 → "(name completed with no output)"  │
│           _spill_large_result(>100K 落盘)             │
│           finalize 回调(结果改写口) → ⑨ post_hook      │
└──────────────────────────────────────────────────────┘
  ▼
批内任一失败?
  ├─ 已完成兄弟保留真实结果(CC review:作废成功读结果是净损失)
  └─ 未启动兄弟 + 后续队列 → <tool_use_error>Sibling tool call errored</tool_use_error>
```

### 设计要点

- **并发屏障**:`is_concurrency_safe` fail-closed 默认 False —— 只有显式声明只读的工具才并行,写工具天然串行。
- **sibling 作废语义(软化版)**:一个失败 → 已完成的保留、未启动的作废 —— 「写失败可能已污染环境,投机兄弟不得执行」;模型必须显式处理失败,不假装成功。
- **三阶段管道**:prepare(权限/校验串行,全部检查过才并发)→ execute(结果按源顺序回报)→ finalize(结果改写集中在单点)。
- **⑨ 钩子入队位置**:PreToolUse 在权限引擎**之前**(prepare 首步),PostToolUse 在 finalize 之后 —— 钩子层只做决策合并不做权限求值(见第 10 节)。
- **生命周期事件**(PI-01):start/update/end 三事件,`on_tool_event` 回调异常隔离(logging,不破坏工具);CLI 消费为 `● name running…` 状态行。
- **spill 幂等**(CC-08):`>100K` 字符落盘,路径按 tool_use_id 确定性生成 —— 重放相同 id 复用文件,prompt-cache 前缀稳定。

## 8. ⑦ 工具契约(tools/base.py)

```
Tool(扁平对象,非类层级)
  name / description / input_schema     ← 元数据,spec() → 模型可见
  is_concurrency_safe = False           ← 并发声明(fail-closed)
  needs_permissions(input) → bool       ← 权限自声明(引擎消费,工具内不自行判断)
  validate_input(input) → raise ToolError ← 执行前校验
  async call(input, ctx) → AsyncIterator[ToolResult]
      ├─ yield ToolProgress(text) 若干   ← 实时 UI,不进模型
      └─ yield ToolResult 一次           ← 最终结果,模型可见
ToolUseContext(cwd, env, abort_event, 读新鲜度状态, read_cache)
ToolResult(content, is_error, terminate, new_messages, metadata)
ToolError(msg, code)                   ← 稳定错误码(PI-12),不解析消息
```

### 设计要点

- **扁平对象 + async generator**;`ToolProgress` 是瞬态进度(只给 UI),`ToolResult` 是终值(给模型)。
- **权限永远在引擎,不在工具内**:`needs_permissions()` 自声明被决策链第 7 步消费;工具作者不为权限负责 —— 与 is_concurrency_safe 自声明同一哲学(契约驱动,引擎保持简单)。
- **terminate 语义**(PI-04):工具可请求「本批后停」,但引擎只在**全批同意**时停止 —— 避免单一工具误判终止(⑩)。
- **ToolUseContext 注入**:引擎构造一次复用于整轮,承载 abort 通道 + Read 新鲜度(`read_file_timestamps/hashes`)+ 去重缓存(read_cache)。

## 10. ⑨ Hook 系统(V0.2 已接线,阶段 09)

> V0.1 中为「阶段 09 预留(pre_hook/post_hook 未接线)」。本版已全量实现:8 类事件、三种执行体(command / prompt / http)、统一管线、双流审计。

### 数据流(统一管线,单点入口)

```
事件触发(8 触点,loop.py 各接线位 → hooks.dispatch / hooks.notify)
  → Stage 0 存在性检查:事件索引空 → 直接返回(零开销)
  → 入口 abort 检查:已置位 → 整批跳过(不决策不审计)
  → Stage 4 输入构建:同批共享一次 HookInput.to_json()(扁平 JSON)
  → Stage 2 匹配与收集:matcher 组级 → if 钩子级(均在 spawn 前)
  → Stage 3 执行层去重:key=(type, payload, if),last-wins
  → Stage 5/6 逐钩子顺序执行 → stdout 解析 → 决策合并
       │ deny 短路:后续钩子不执行,审计记 skipped
       │ abort 感知:跳过剩余,审计记 cancelled
  → 聚合:additional_context / updated_system_reminder join('\n\n')
          updated_input last-wins;hook_allowed = verdict=="allow"
  → PreToolUse 有决策 → 恰好一条权限审计(audit.jsonl)
    每钩子恰好一条 hooks.jsonl 审计(含 skipped/cancelled)
```

### 事件触点与决策语义

| 事件 | 触发位置(loop.py) | 决策语义 |
|---|---|---|
| `SessionStart` | run() 入口,门闩一次 | 非阻塞;exit 2 忽略;`additionalContext` 累积进一次性 `_hook_reminder` |
| `UserPromptSubmit` | 首条输入 / steer 中途输入 | exit 2 → 首条 `_stop("hook_blocked")`、steer 静默丢弃;`updatedPrompt` 替换后建消息 |
| `PreToolUse` | 工具队列 prepare,先于权限引擎 | fail-closed:deny / allow 短路 / updatedInput / immune(见下) |
| `PostToolUse` | finalize 之后(成功与拒绝都触发) | 观察型:失败仅日志不改结果 |
| `Stop` | completed / tool_terminated 分支 | `continue:false` → `_stop("hook", stopReason)`;exit 2 → feedback 注入用户消息(≤5 次) |
| `PreCompact` | `_compact` 内,切点后、摘要前 | exit 2 → 阻断本轮压缩;instructions 注入摘要 prompt |
| `PostCompact` | 压缩成功返回前 | 纯观察 |
| `Notification` | permission_request / permission_denied / tool_error / llm_error 四处 emit | 全 fail-open,不产生权限审计 |

### PreToolUse 决策落位(loop.py `_pre_tool_use_hook`)

```
dispatch("PreToolUse", input + tool_name/tool_input/tool_use_id)
  ├─ dispatch 异常 → fail-closed:审计 deny + 返回拒绝 ToolResult
  ├─ updated_input → 改写 item.input(先于引擎)
  ├─ item.hook_allowed / item.immune 落位
  ├─ decision="deny" → 拒绝 ToolResult(error_code=permission_blocked)
  ├─ hook_allowed → 引擎短路(唯一例外:写保护地板 floor_check 命中
  │                   → 降级 request_permission 人工确认)
  └─ 返回 None → 继续走 ⑤ 权限引擎
```

### fail-closed / fail-open 表

| 失败类型 | PreToolUse | 其他事件 |
|---|---|---|
| JSON 解析/校验失败(stdout 以 `{` 开头) | **deny** | 非阻塞错误,流程继续 |
| 超时 / spawn 失败(含 shell 中介 exit 127) | **deny** | 非阻塞错误 |
| exit 2(blocked) | **deny** | 按事件消费(上表) |
| exit 1 / 其他 | fail-open | 同左 |
| 钩子自身 bug(非 HookError) | **deny**(dispatch 兜底) | 非阻塞 + 日志 |

原则:**钩子「没能说话」→ 安全门关闭(deny);「说了话只是抱怨」(exit 1)→ 放行。**

### 执行体三型

| 执行体 | 输入通道 | 要点 |
|---|---|---|
| command | stdin = HookInput JSON | 子进程 cwd 取自输入 JSON;Windows 优先 Git Bash(复用 `bash._shell_argv`);超时 → 进程树击杀;stdout 捕获限额 256KB(截断 JSON 自然 fail-closed) |
| prompt | `$ARGUMENTS` 占位符替换 | 单轮 LLM 请求(`model="quick"` 指针),强制 JSON;`ok:true` → exit 0 / `ok:false` → exit 2 + reason |
| http | body = HookInput JSON,POST | URL 白名单 + SSRF 矩阵(域名先解析逐地址判定)+ header 白名单插值 + CRLF 消毒;必须返回 JSON |

### 设计要点

- **统一管线单点**(registry.py `_run_pipeline`):全部事件唯一路径,匹配/去重/执行/决策/审计集中 —— 决策合并与审计不变量只在一处维护。
- **fail-closed 只针对 PreToolUse**:防泄漏事件(exit 2 之外)全 fail-open;deny 复用 `permission_blocked` 错误码 → 自动获得 sibling 豁免语义。
- **PreToolUse 先于权限引擎,但不替代它**:钩子层只做决策合并不做权限求值,「权限判断永远在引擎」不变量保持(CLAUDE.md 核心不变量 #5)。
- **写保护地板是 allow 短路的唯一例外**:`hook_allowed` 短路引擎时,写保护路径仍降级为人工确认 —— 不变量「写保护路径优先于 allow」无例外。
- **审计双流、每钩子恰好一条**:hooks.jsonl 执行流(含 skipped/cancelled,stderr 前 200 字符)+ audit.jsonl 权限流(仅 PreToolUse 有决策时,source=`hook:PreToolUse`);钩子输入输出不落审计(防密钥)。
- **matcher 三级匹配**:空/`*` 全匹配 → `|` 精确列表 → 正则;UserPromptSubmit/Stop 忽略 matcher(`MATCHER_IGNORED_EVENTS`);`if` 条件复用权限规则语法,仅 Pre/PostToolUse 可求值。
- **快照语义 + 无信任门**:配置构造时一次装配(索引/执行体/去重冻结),会话中不热载;信任 = 配置即信任,缓解 = 快照 + 写保护地板 + 双流审计。
- **执行体隔离**:HTTP 执行体每请求新建 client,不共享 LLMClient 的 VCR transport;SessionStart 的 http 钩子直接剔除(关键路径不依赖外网)。

## 11. ⑩ 终止与恢复语义

| 原因(last_stop_reason) | 触发 | 产物 |
|---|---|---|
| `completed` | 模型终答(无 tool_use) | 正常结束 |
| `max_turns` / `max_budget` | 检查点 1 | is_meta 说明消息 |
| `interrupted` | abort(三检查点) | `(interrupted by user)` is_meta |
| `tool_terminated` | 批内**全部**工具 terminate(PI-04) | `Stopped: tools requested termination.` |
| `thinking_only_exhausted` | 3 次 thinking-only 恢复重试后 | is_meta 放弃消息 |
| `hook_blocked`(V0.2 新增) | UserPromptSubmit 钩子 exit 2(首条输入) | is_meta 说明消息 |
| `error` | 不可恢复 LLMError | `(provider error: …)` is_error 消息 |

### 设计要点

- **结构化终止原因**(CC-10):`last_stop_reason` 替代文本嗅探,CLI/测试按原因分支(`--output-format json` 暴露 `max_turns_exceeded` 等)。
- **terminate 全批同意**:逐个工具检查 `result.terminate`,全 True 才停;检查放在结果已 yield 之后 —— 模型/用户仍能看到工具做了什么。
- **thinking-only 有界重试**:恢复消息不计轮次(`turn -= 1`),重试预算与轮次预算是两个独立有界维度。
- **压缩不是终止条件**:⑭ 压缩自身失败走错误路径,不产出 stop_reason;钩子自产的 stop 不再触发 Stop 钩子(防递归)。

## 14. ⑬ 上下文工程(V0.2 新增,阶段 08)

> 会话级上下文的**一次性组装器**:AGENTS.md 逐层收集 + git 快照 + 日期 → ContextBundle → 每轮渲染为前置 user 消息注入。memoize 在调用方(CLI 启动一次,loop 内零重建)。

### 数据流

```
CLI 启动(build_loop, assemble.py,会话一次)
  └─ build_context_bundle(cwd) [engine/context.py]
       ├─ currentDate 生成
       ├─ _git_snapshot: 3 条 git 命令并行(线程池)→ 非仓库跳过
       └─ AGENTS.md: 逐层向上收集(远→近)
                    → _apply_budget(32KB,近因优先)
                    | _read_override(整体替代)
       └─ ContextBundle(sections) → AgentLoopConfig → AgentLoop.context_bundle

每轮 _ask_model(engine/loop.py)
  ├─ _consume_prefetch():已完成 prefetch 段落 append 历史末尾
  ├─ normalize_for_api(history)  [is_reminder 前置合并,summary 保位]
  ├─ prefix = [_render_reminder(bundle)]   ← 唯一注入点
  │            (fixed 恒留 + agents 近段,≤10 段)
  │          + [_recovery_reminder]  压缩后一次性(最近修改文件)
  │          + [_hook_reminder]      钩子 additionalContext 一次性
  ├─ api_messages = prefix + normalized
  └─ LLMRequest(system=静态 base, messages=api_messages) → client.stream
```

### 数据形状(sections 固定三段,顺序即渲染顺序)

| title | 内容 | 来源 |
|---|---|---|
| `currentDate` | `Today's date is YYYY-MM-DD.` | 内联生成 |
| `gitStatus` | branch + 最近 5 条 commit + status --short(截 2000 字符);非 git 仓库跳过 | `_git_snapshot` |
| `agentsMd`(可多条) | 每层目录一个 AGENTS.md 内容 | `_collect_agents_files` + `_apply_budget` |

### 设计要点

- **会话一次 memoize、零失效**(CC-13 裁剪):AGENTS.md 会话中修改不重载 —— 单进程单目录会话中无变更源;resume 时由 bundle 重建,不与对话历史耦合。
- **预算与段上限,近因优先**:AGENTS.md 总预算 32KB(近文件完整保留,第一个溢出文件截断,更远丢弃);渲染上限 10 段(date/git 恒保留,agents 丢最远)—— 与预算策略一致。
- **reminder 只进请求,不进会话**:渲染产物是普通 `ai.Message(role="user")`,非 SessionMessage —— 不持久化、不参与 normalize,会话文件里永远看不到(测试断言)。
- **前缀字节稳定,配合缓存**:system 静态 + reminder 前置保证前缀稳定,配合 DeepSeek 自动前缀缓存 / Anthropic cache_control 断点;⑭ 摘要走 compact 指针不污染主链前缀。
- **normalize 侧契约**:`is_reminder` 消息抽离合并为一条 user 消息**插入输出最前**;`is_compaction_summary` 永不与相邻 user 合并(两条独立规则,core/normalize.py)。
- **无段级开关、无增量更新**:唯一控制是 override_file(整体替代 AGENTS.md)与渲染器 10 段裁剪;增量/去重留待阶段 17 记忆系统。
- **三个注入通道共用 prefix 机制**:context bundle(每轮) + recovery reminder(压缩后一次性) + hook reminder(钩子一次性),顺位固定,注入后清除。

## 15. ⑭ 压缩系统(V0.2 新增,阶段 10)

> O(n²) 上下文增长的解法:turn 顶部检查点触发,摘要压缩旧历史,消息列表保持有界。触发决策在 loop.py 检查点,机械实现(切点/序列化/摘要)在 engine/compaction.py。

### 局部流程(触发 → 决策 → 执行 → 替换)

```
触发(检查点,loop.py turn 顶部,turn += 1 之后、_ask_model 之前)
  ├─ auto:  microcompact(clean_old_tool_results,零 API 成本)
  │         → estimate_context_tokens(清理视图,usage 锚点)
  │         → should_compact = tokens > window - reserve(128K-16.4K = 111,616)
  └─ PTL:   _ask_model 抛 PTL 错误(413 / context_length_exceeded)
            → 跳过阈值,强制压缩(每轮 run 至多一次,防死循环)

执行 _compact(loop.py)
  1. find_cut_point(messages, keep_recent=20K) → CutPoint | None
       · 合法性:user/assistant/summary 边界;tool_result 载体永不切
       · user 边界 → 切整轮;assistant 边界 → 拆轮(turn_prefix 单独摘要)
       · 尾部不足 keep_recent / i==0 → None(无物可压)
  2. PreCompact 钩子(exit 2 → 阻断本轮)
  3. generate_summary(model="compact" 指针,走 client.complete)
       · serialize_conversation:<conversation> 包裹,工具结果截 2000 字符
       · 有旧摘要 → UPDATE_SUMMARIZATION_PROMPT(增量更新,不重写)
       · 摘要请求 PTL → _drop_oldest_turn 截断,恰好重试 1 次
  4. FileOps 合并:实际执行成功的 Read/Write/Edit 路径,跨轮去重
  5. _persist:append-only 追加一条摘要消息
  6. PostCompact 钩子(纯观察)

消息替换:state.messages = [summary_msg, *messages[cut.index:]]
  + _recovery_reminder 下一轮一次性注入(最近 ≤5 个 modified 文件,每文件 ≤20K 字符)
```

### 数据形状

- **CompactionConfig**:`enabled`(熔断可置 False)/ `window`(128K,profile 无 context_window 的兜底)/ `reserve`(16,384)/ `keep_recent`(20,000)。
- **摘要消息**:`user_message(text, is_compaction_summary=True)` —— role 为 user,8 节结构由 SUMMARIZATION_PROMPT 规定(Goal / Constraints / Progress / Key Decisions / Next Steps / Critical Context —— 关键路径/命令/URL 原文存活),尾部可选 `<read-files>` / `<modified-files>` 段;normalize 保位不合并。

### 设计要点

- **双触发语义**:auto 阈值前置(估算用清理后视图、摘要生成对 RAW 消息 —— 保真不损);PTL 反应式跳过阈值强制压缩,`ptl_retried` 保证每轮 run 至多一次;PTL 压缩失败落入外层错误路径,无 PTL-压缩-PTL 死循环。
- **microcompact 先行**:清理请求视图(旧工具结果)是零 API 成本的第一道闸,清理释放足够 token 时 LLM 摘要根本不触发。
- **防抖与熔断**:`turn != _last_compact_turn` 每轮至多一次;连续 2 次摘要 LLMError → `compaction.enabled = False`(同时锁死 PTL 反应式路径),成功清零;`cut is None` / PreCompact 阻断 / 钩子失败不计熔断。
- **摘要迭代(UPDATE)**:第二次压缩把上次摘要也交给模型更新(在压缩段内找 `find_previous_summary`)—— 省 token、信息不丢。
- **append-only 一致性**:磁盘只追加、内存才替换;`--continue` 重放按 `is_compaction_summary` 定位 —— 压缩是「标记型消息」而非删除。
- **压缩不计轮次、不是终止条件**:摘要请求不使 `state.turn` 前进;压缩自身失败走错误路径,`last_stop_reason` 无压缩相关取值。
- **缓存配合**:摘要走 compact 指针,与主链隔离不污染主链前缀缓存;摘要消息保位不合并,系统 prompt 字节稳定原则在压缩场景延续。

## 16. 总览:横切设计原则

1. **单一信息通道**:Message 流是唯一通道 —— 工具结果、中断、错误、终止都是消息,消费方对内部机制无感知。⑬⑭ 的注入(reminder / 摘要)也是消息,不新增通道。
2. **错误自愈**:工具失败转 error tool_result 交模型调整,循环永不崩;唯一硬性停止是有界预算。Hook 失败分两类:PreToolUse fail-closed(安全门),其余 fail-open(不打断)。
3. **安全默认**:ask 无回调 → 拒绝;未知工具默认 ask;并发 fail-closed;deny 不可绕过;钩子「没能说话」→ deny;HTTP 钩子 URL 白名单 + SSRF 矩阵。
4. **有界性**:max_turns / max_budget / 重试次数 / 结果落盘阈值 / 清理预算 / 压缩 keep_recent / Stop hook feedback(≤5 次)/ 摘要 max_tokens 全部有界。
5. **可测可注**:依赖全部构造注入,session 可选,queue 可断言,ContextBundle 会话一次可替换 —— 797 项测试全绿。
6. **契约驱动**:并发安全、权限需求都由工具自声明,引擎保持简单、单点决策;Hook 输入输出是扁平 JSON 契约(schema 校验),决策合并集中在管线单点。
7. **注入即隔离**(V0.2 新增):上下文 / 压缩 / 钩子的消息改写全部走「prefix 前置 / 新消息追加」通道,内容不进会话日志、不参与 normalize,前缀字节稳定配合缓存 —— 三个新系统都不破坏消息契约唯一形状。
