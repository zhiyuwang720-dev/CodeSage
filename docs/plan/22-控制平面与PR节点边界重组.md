## 1. 决策与目标

重组为“**可替换的控制面实例 + 可独立运行的 PR Agent 节点 + 外置权威状态**”。继续使用 Python、FastAPI、ARQ、PostgreSQL、Redis、LiteLLM 和现有 Harness，不整体移植 AgentField，不以重新开发平台代替审查能力建设。

控制面三模块采用用户提出的分类，但作如下定义：

1. Runtime & API：接入、运行命令、运行查询、SSE、执行记录和版本化节点协议。这里的 Runtime 是运行生命周期，不是模型 QueryLoop。
2. Scale & Ops：持久化投递、领取/续租、取消、任务级重试、背压和节点健康。跨节点 DAG 是未来能力；当前 PR 内的视角、分包、coverage 属于 PR 节点。
3. Identity & Audit：管理员与节点身份、运行授权、工具能力约束、持久化安全事件。DID、VC、签名审计包与不可否认性不纳入本轮。

“无状态”指控制面进程内不保存唯一事实来源，不等于无数据库、无执行状态。数据库保存 run/attempt/lease/cancel/result receipt；队列负责投递，不作为业务事实来源。SSE 连接允许保存在当前进程，但断连/进程重启不能导致业务记录丢失。

验收后的直接收益：PR 新增阶段、工具或分包策略不再修改通用控制面；API/worker 不再反向导入业务私有入口；21A 能力保留；数据库事务和恢复保证不因目录重命名而削弱。

## 3. 范围和非目标

Plan22分22A、22B、22C三个实施阶段，分别验收；21B插在22B与22C之间。22C已纳入开发顺序，不能用22A/B完成宣称整个Plan22完成。

- 22A：模块归属、数据模型所有权、端口和单一事务边界。
- 22B：独立控制面/PR 节点启动、版本化投递信封、背压和节点故障回归；同一台电脑上的真实双节点进程。
- 22C：21B验收后，实施远程节点协议、无平台DB凭据的节点、结果接收与业务投影解耦；本地多容器验证，不要求购买远程机器。

不做：新模型协议、新 Agent、通用自动 DAG、Kubernetes、云服务器、S3、DID/VC、复杂组织权限、替换 SessionStore、重写 QueryLoop、扩大真实模型付费测试、以 OTel 替代 Checkpoint。保留离线评测 JSONL/HTML 输出，不迁回数据库。

## 4. 目标目录与依赖规则

```text
backend/app/
  api/                         # HTTP 适配器；路由按平台与 PR 产品区分
  control_plane/
    runtime_api/               # 运行命令、查询、版本化节点注册/调用契约
    scale_ops/                 # queue、attempt、lease、取消、背压
    identity_audit/            # 身份、授权、运行安全事件
    persistence/               # 控制面 ORM/repository
  nodes/pr_review/
    application/               # 提交/恢复、输入准备、快速流程协调
    domain/                    # diff、视角、证据、coverage、完成门禁
    tools/                     # PR 工具与代码图适配器
    contracts/                 # PR 专用身份、输入、StageResult、Findings
    persistence/               # PR ORM、阶段/结果 repository
  node_runtime/
    harness/                   # QueryLoop 与执行控制
    sessions/                  # 恢复、会话、运行时记忆
    llm/                       # 现有 LiteLLM 薄封装
    tool_gateway/              # 通用工具调用、策略执行和限额
    persistence/               # session/receipt/checkpoint 映射
  contracts/platform/          # 无 ORM/HTTP/ARQ 依赖的跨边界信封
  infrastructure/             # DB、文件产物、Git、OTel 等具体适配器
  bootstrap/                  # API/worker 的依赖装配和事务桥接
```

这是目标归属，不要求把每个目录拆成一个进程、包或微服务。执行者应移动现有文件，避免建立只有转发作用的多层 manager/facade。

强制规则：

1. 通用控制面不得导入 `nodes.pr_review`、`node_runtime.harness`、LiteLLM 或 PR 提示词。
2. `node_runtime` 不得依赖 PR 业务；PR 节点可以依赖它及平台纯契约。
3. API 可以调用平台命令或 PR 产品应用服务，但不得含 QueryLoop、Git 命令或结果事务实现。
4. 通用投递器只识别 `agent_type + entrypoint + version`；处理函数在 bootstrap 显式注册，禁止由请求指定任意 Python import path。
5. PR 的 `quick_review` 只协调；stages/findings/final artifact manifest 的持久化只经 PR 结果服务。平台只提供通用 ownership guard 和提交上下文，不知道 security/quality 等阶段名。
6. 22A/22B 的结果事务由 bootstrap 的 UnitOfWork 适配器把 PR 结果写入和平台终态置于**同一数据库事务**。repositories 不自行 commit。业务分层不等于拆事务。
7. 共享基础设施是技术复用，不是共享所有权；控制面不得通过“公共 repository”读取节点 Session 内容实现编排。
8. 兼容导入必须登记调用者、替换目标、删除阶段。内部调用在 22B 结束前迁完；HTTP 对外兼容不要求同时删除。

- Alembic metadata 由统一登记入口收集所有映射；移动后需证明没有遗漏表、重复 mapper、关系解析错误。

## 7. 22B：独立节点与控制面进程验收

### B1 独立入口

- 控制面 API 入口只初始化平台与产品 HTTP 适配器，不启动模型执行；PR 节点独立 ARQ 入口装配 PR handler 与 node_runtime。
- 本地 PostgreSQL/Redis 与共享产物根保持现状，两个节点进程独立 PID、node_id、并发上限；平台进程不得持有 LLM 服务实例。
- 节点定义 `agent_type=pr_review`、支持的 entrypoint/version、最大并发、能力集。初版由配置 allowlist 注册，健康记录持久化/可重建；不做公共自注册服务。
- ARQ 的调度粒度保持完整 review；平台不投递每个视角/包。
- 同主机共享路径是明确的部署前提，不宣称已支持任意远程节点。

### B2 命令、取消、恢复和背压

- 投递消息携带版本化信封和 trace context，不带完整 diff、prompt、模型密钥；任务输入内容经受控引用读取。
- 发送前持久化 delivery_id；入队失败/不确定可以用同 delivery_id 重试。ARQ 去重与 DB owner fencing 都保留，不互相替代。
- 领取成功后产生 attempt_id/epoch；节点心跳与运行租约心跳分开，节点健康不能越权替代有效 lease。
- 明确运行并发上限、待执行上限与超限拒绝/延迟策略，配置默认值和错误响应；不得用内存 semaphore 充当多进程全局上限。
- cancel 先落库；resume 检查 PR 输入身份/配置兼容，再创建新 delivery。已完成阶段不增加模型调用数。
- 明确唯一任务级 retry owner；模型请求级 retry 留 LiteLLM/模型层。禁止平台重试、ARQ 重试、节点重试叠加无界放大。
- 单消息崩溃接管测试报告必须列出 job_timeout/max_tries、lease、重试间隔。不得再次投递伪装自动接管；不能通过过短 timeout 杀掉正常长审查来换取通过。

Spec22B将此项具体化为：Scale & Ops reconciler是唯一业务重投递决策者，持久化logical delivery与physical dispatch，锁内确认lease过期后自动补投。验收禁止测试端手动补投；系统自动补投允许且必须完整记录。保留长任务timeout，不能假设ARQ在owner死亡后天然90秒回队。

### B3 可观测性归属

- 平台记录 submit/queue/claim/cancel/resume/commit；节点记录 preflight/review/perspective/turn/model/tool/checkpoint。
- OTel context 随投递信封跨进程传播，run/attempt/stage/session 等 ID 正确关联；恢复 attempt 建新 span/trace 并保留 link，不伪装一个进程存活的 span。
- 模型成本/token 只从物理模型请求事实聚合一次；平台父 span 不再重复产生费用。完整 prompt/工具正文仍按现有采集策略与产物引用处理。
- 业务审计、可丢弃诊断、恢复 checkpoint 三者不能共用“日志失败忽略”的错误处理。
- 离线评测直接导出 JSONL/静态 HTML；控制面数据库只维持生产运行事实，不成为展示评测的强依赖。

### B4 集成验收

使用现有确定性模型替身、真实 QueryLoop/SessionStore、PostgreSQL、Redis、两个独立 PR 节点；不调用付费模型。

| 测试 | 必须证明 |
|---|---|
| 完整运行 | 快照、三视角、完成门禁、Findings、产物哈希与既有基线一致 |
| 双节点并行 | 两个不同任务分别被不同 node/PID 持有，执行区间重叠 |
| API 重启 | 运行不丢失；重新查询/连接 SSE 可从持久状态继续 |
| 跨进程取消 | 10 秒内停止新增测试模型请求，晚返回不能覆盖 cancelled |
| 取消恢复 | 新 attempt、同 identity；已完成视角零重跑 |
| 单消息崩溃接管 | 杀 owner，无第二次人工投递；按声明配置满足接管时限，默认沿用原 90 秒目标 |
| 重复投递/旧 epoch | 仅一个有效 owner；旧 owner 阶段/Findings/终态写入全拒绝 |
| SSE 与结果错误分离 | SSE 失败不破坏结果；结果提交失败不出现假 completed |
| 身份/产物损坏 | 不兼容输入、篡改产物、越界路径模型调用前或复用前拒绝 |
| 背压 | 达限时可解释地拒绝/等待，两个节点总并发不超限，无任务静默丢失 |
| 平面隔离 | 平台进程无模型执行；PR handler 不绕过所有权服务写平台终态 |

正常运行、取消恢复、崩溃恢复各连续三次；使用持久化屏障控制故障时机。报告不得把本地多进程称为跨机器验收。

## 8. 22C：21B之后的远程节点与结果投影

远程进程不应持有平台 DB 写权限或依赖平台本地绝对路径。需要内部 claim/heartbeat/checkpoint/finish 协议、输入/产物传输、节点凭据和撤销机制。

最重要的事务变化：跨服务后不能把“节点 DB 写 Findings”和“平台 DB 写 completed”当作一个本地事务。届时采用不可变结果 manifest + fenced 提交 receipt + 平台 outbox + 幂等 PR 结果投影；平台原子提交 receipt/终态/outbox，产品审查状态只有投影成功后才显示完成。投影失败可重试且可查询，不由节点晚到回调覆盖。

该阶段通过Alembic实施AgentRun与PRReviewJob的逻辑分离，将PR identity与平台lease所有权分开，保留旧ID映射与API兼容；物理旧表删除另行验收。远程会话、work unit、覆盖与预算经RecoveryManifest持久化，不能只传最终报告。不能提前声称只改目录就已形成安全隔离的Fleet。

## 9. 交付、进度与完成标准

每一阶段独立提交：A0 基线 → A1 契约/装配 → A2 PR 归位 → A3 runtime/ORM → A4 裁剪 → B1 独立入口 → B2 故障/背压 → B3 观测 → B4 验收。

进度字段：状态仅用 `not_started/in_progress/implemented/blocked/verified/retest_required`；每项填写 commit、变更路径、测试命令/退出码、报告、未解决问题。移动文件的提交不同时改变提示词、模型、完成门禁。

| 项目 | 状态 | 证据 |
|---|---|---|
| A0–A4 | not_started | 待执行者填写 |
| B1–B4 | not_started | 待执行者填写 |
| 22C | not_started | 21B签收后实施；详见22C Spec与统一台账 |

22A 完成：所有权与依赖边界可由测试执行，既有事务/恢复无新增失败，21A 能力保留。

22B 完成：两个真实节点跑完故障矩阵、平台 API 可重启、版本化投递与背压可解释、观测不重复计费、有一条本地复现命令和完整报告。

22C完成：远程协议/TLS/授权、非共享根恢复、session/unit/budget Checkpoint、fenced receipt/outbox与幂等投影全部通过隔离验收；本阶段不承诺企业吞吐或真实跨机性能。

预估：22A 约 5–8 个有效开发日，22B 约 4–7 日；这是根据现有耦合做的工作估计，不是承诺。基线故障和 API 裁剪消费者数量可能增加工作量。22C 不包含在估算内。

## 10. 后续能力优先级

21A → 22A → 22B完整阶段验收 → 21B确定性分包/覆盖/预算恢复 → 22C远程协议/结果投影。各阶段沿offline benchmark输出对照，之后根据数据选择critic/coverage或工具改进；21M单独选型验收。

远程PR节点协议已纳入22C；多类Agent与通用工作流仍须实际需求驱动。不要为了架构图先构建营销/客服节点，也不要用目录整洁度替代PR审查效果。
