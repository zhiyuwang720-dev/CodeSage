## Plan Draft、repair 与执行干扰

- Linera 原始 Draft 与最终四维度均保留问题；`quorum-grace-semantics` 明确要求检查负值/NaN，`api-surface-and-consumers` 明确要求检查错误字符串。报告的 3 条 Candidate 不等于只调查了三件事。
- mpv 原始 Draft 五维度，repair 把 `build-and-assert-contract` 完整包含的调查并入 `prng-core-semantics`，保留编号调查和 cross hint；不是本次漏报的主要删除点。
- Ollama 原始和最终均八维度。多个维度有重叠 target，某些 `review_prompt` 给出了很细的故障假设，既有锚定风险也占用审查轮次；不能仅凭“文件有 owner”宣称所有具体问题都被核实。
- SQLite 记录：Linera 76 次成功工具调用、0 次失败；mpv 91 成功、2 失败；Ollama 201 成功、8 失败。失败中 mpv 两次、Ollama 一次把未变更 context 文件交给 `file_read_diff`；Ollama 一次非法正则、两次搜索问题、若干 `file_read` 超时。单独重放 Ollama 的 `git show` 与 `git grep` 约 0.1–0.2 秒，不能据此断言原超时是稳定的仓库性能问题。
- Linera 5 个 Harness session 中 3 个出现追加终结提示；mpv 5 个中 2 个；Ollama 的 Planner 与 8 个 Reviewer 全部出现。追加终结说明模型未在主循环中提交完整结构化结果；不能单凭它证明思维断裂。Ollama 多个 Reviewer 触及各自的 8/12 turn 上限，但本包不调整上限。
- Ollama 的 Candidate C6、C8、C9、C10、C12 在文字中描述性能小建议或已验证匹配/无错误，却进入 findings。它们应在后续实测中作为 worthiness 失效样例；不能用 Candidate 总数衡量召回。

报告中 `agent_observations` 的输入/输出 token 求和分别是：Linera 80,479/8,978，mpv 122,635/17,282，Ollama 223,399/16,920。这是既有运行各阶段的记账量，不等于去重后实际计费 token。`cache_read_tokens` 只有各例 Semantic 阶段非空（2,688、3,072、8,960）；其他 5/5/9 个观测为空，不能把缺失值当作零，也不能从这些数字断言终结时缓存命中。三例 `cost_usd` 均未形成可靠总额，因此成本保持 `None`。

复核方法：按 case 从 JSONL 中取得 `reference_comments`，在对应报告中查看 `plan.dimensions`、`repair_actions`、`candidates`、`agent_observations`；Planner 原始维度位于该 case `sessions.sqlite3` 的首次 `FinalizeReview` 工具输入。工具失败用 `audit_tool_calls.status != 'completed'` 查询，追加终结用 `audit_session_messages.name LIKE 'runtime_finalizer%'` 查询。查询必须只读，不覆盖这些历史文件。
