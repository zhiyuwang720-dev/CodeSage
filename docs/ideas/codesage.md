# CodeSage — Harness 框架(学习 + 未来改造)

## Problem Statement

如何构建一个 Python Harness 框架,让一个人既能彻底学会、又能日后自由改造 agentic 编程助手的每一个模块?

## Recommended Direction

**教科书型**:模块边界来自「harness 需要什么」的理论,功能清单以 Kode-CLI 为参考地图、Claude Code 为补充。不做 Kode 结构 1:1 镜像(TS monorepo 的边界是基础设施驱动的),Python 侧从现有代码形状出发(`service/llm`、`service/agent`、`service/runtime`、`service/core`)。

每个阶段 = 一个模块全量完成 + 一份中文理解文档 + 系统保持可运行。V1 为最小闭环(REPL + 单模型 + 核心工具 + 权限门控),V2+ 逐模块加深,热插拔注册层为收尾阶段。从 V1 起守住「模块边界干净」纪律,后期热插拔只是加注册层而非重构。

**安全设计位置**:权限运行时从第一天带审计事件钩子(轻量),完整威胁模型/沙箱推迟到安全领域适配阶段。

## Key Assumptions to Validate

- [ ] Python 异步生态(httpx/anyio)能干净表达 harness —— **已验证**:LLM 模块即证据
- [ ] Kode 功能清单 ≈「harness 需要什么」的完整地图 —— 以 Claude Code 行为为补充参考
- [ ] 审计钩子在权限运行时的成本趋近于零 —— 设计为一个事件回调,不加框架
- [ ] 每个模块都能在「当前最大深度」内找到完成线 —— 每阶段文档需写死完成标准,防范围失控

## MVP Scope(V1 = 最小闭环)

阶段顺序(待 spec 细化):

1. **01 LLM 客户端** — 保留精修 + 补文档(已有:adapters/factory/protocols/types)
2. **02 Agent 核心** — 循环、消息、状态(重做现有半成品)
3. **03 工具系统** — 基类、注册、内置工具(重做)
4. **04 权限系统** — 门控 + 审计钩子(重做现有 runtime)
5. **05 任务/会话系统** — 会话持久化、任务执行
6. **06 CLI 交互层** — REPL,端到端完成一个小任务(闭环验收)
7. 后续:上下文管理 → 技能系统 → MCP 客户端 → 子代理编排 → 多模型编排 → 热插拔注册层

## Not Doing (and Why)

- **框架型(公共 API + 插件注册层从第一天起)** — 只有一个实现时接口是猜出来的;热插拔留到有 ≥2 个真实实现之后
- **复刻型(1:1 镜像 Kode packages)** — TS 边界污染 Python 设计
- **垂直切片型(按安全工作流排模块顺序)** — 扭曲「每阶段一个完整模块」的节奏
- **桌面/Web/VS Code/Server 客户端、富 TUI、MCP 服务器端** — 学习项目一个 CLI 足够
- **完整安全前置(威胁模型文档、沙箱语义)** — 推迟到安全适配阶段,只保留审计钩子
